# D016: A catalog entry owns only the commands it declares, and an install that exports more stays off PATH

[← Decision Index](INDEX.md)

**Date**: 2026-09-10 **Status**: Active **Research**: — **Refines**: [D011](D011-mise-owns-agent-harnesses.md), [D014](D014-command-provenance-and-duplicates.md)

**Context**: [D014](D014-command-provenance-and-duplicates.md) tests a catalog row against the one command the row declares, and treats two copies of that command as the failure to resolve. A package is not only the command VGS asked for. The Cursor Agent package ships `node`, `rg`, `cursor-askpass` and a dozen more beside its own binary, and mise's registry entry exports the whole package directory. mise's bin path sits ahead of `/usr/bin`, so `node -v` reported the package's 24.5.0 while `/usr/bin/node` was 26.8.1 and `npm` printed a Node-version warning on every invocation, with nothing on the machine saying why. `rg` was replaced the same way. Both replacements reached every process the session started, on every machine that installed the row.

**Decision**: A catalog entry owns the command it declares, the file its `exec` path names inside the package, and the executable its launch argv names. Nothing else the install exports belongs to the entry, another name for one of those files included: the `agy` package ships `agy` as a link to `antigravity`, and `antigravity` is judged like any other export.

An entry whose package exports more keeps the package's own directory off PATH. Its spec carries an empty mise `bin_path=`, which moves the export from that directory to the install root, and its `exec` field names the file under the root that the stub and the launcher run by absolute path. `mise x` would find no executable of the tool's name inside the package and fall through to PATH, where the stub in `~/.local/bin` answers again. The stub and the launcher both resolve the root with `mise where`, so one install answers both. `bin_path=` alone settles nothing for an archive holding an executable at its top level, since the install root is on PATH; the export check catches that shape.

`mise_sync` in `bin/vshell_mise.py` holds the rule where the spec cannot. `vshell mise refresh` runs it, and so does every `vshell update run tools` after `mise up`. It rewrites the stubs, re-declares options as described below, then asks mise which executables each installed agent, app and tool exports (`mise bin-paths --json`) and walks PATH for every exported name the entry does not declare. `command_on_path_elsewhere` judges each hit by two tests. Same install: a hit that resolves to one of the install's own files or to the mise binary is the install under another name, as a link inside the package, mise's `latest` directory and every mise shim are, and is passed over. Shadowing: the install replaces a copy only when its own first answer for that name comes before the copy on PATH, so a copy that answers ahead of it, such as the owner's wrapper in `~/.local/bin`, is passed over as well. The first hit left is a conflict. Where the install answers nowhere on the PATH the check runs with, every other copy counts, because the owner's shells may carry the directory that PATH lacks. The declared set comes from the entry; there is no second list and no exemption list.

The check leaves two kinds of install out. An `envs` row installs toolchains with `mise use -g`, and their exports answer ahead of the distribution's because that is what the row is for. A row's `requires` packages are installed globally by the same steps that install the row, and the check does not ask about them: on the machine this was filed from, the Hermes row's `uv` answers ahead of `/usr/bin/uv`. Covering them is separate work, because under the failure rule below a `requires` conflict would fail every update with nothing in the Developer tab that could clear it.

A conflict and a check mise could not answer are both failures. `mise_sync` returns one outcome that passes only when every part passes and carries every part's error, and `vshell update run tools` and `vshell mise refresh` exit non-zero on it. The Cursor row shipped with nothing reporting the shadowing, and a notice above a passing exit would leave a supervisor reading the exit code no better off. No install path runs the check: the first-launch prompt, the Replace with mise action and a stub's own first run all leave it to the next refresh or tools update.

mise copies a spec's backend options into the global config the first time a tool is used and never revisits them: `mise up` moves the version and leaves the options as recorded. `mise_sync` therefore re-declares every installed entry whose spec carries options. A spec carrying no option is not re-declared, yet mise may hold options for it from its registry: the Cursor row's plain spec recorded `bin_path = "dist-package"`. A change that removes an option from a row's spec therefore carries its own re-declaration.

Once an entry with an `exec` path has its options recorded, its launcher in `~/.local/bin` is the only way to run its command from a shell, so VGS changes that route only through a launcher it owns. `launcher_advice` in `bin/vshell_mise.py` is the one judge: VGS owns the launcher when the file is its own stub. Every step that records such an entry's options asks it first and records nothing otherwise: the re-declaration, the Developer tab's Track action, and the install the first-launch prompt and Replace with mise share; a stub's own first run is that launcher. When VGS does not own it, the judge names the cause and the command that clears it: the owner's own file, which must run the binary by absolute path before `mise use -g '<spec>'`; auto-install off, cleared by `vshell mise opt-in`; the command already answering elsewhere, which ends once `mise use -g '<spec>'` retires the package's earlier export and the next refresh writes the launcher; or a launcher not yet written, cleared by `vshell mise refresh`. `mise_sync` prints that advice for a kept entry whose install still shadows a copy. Turning auto-install off (`vshell mise remove-stubs`) keeps the launcher of an installed entry with an `exec` path, and of every such entry when mise cannot say what is installed, lists it as kept, and fails in that second case.

**Rationale**:

- The declaration already exists. `command`, the `exec` file and the launch argv's executable are what the catalog says an entry is for, so the rule needs no new vocabulary and cannot drift from the rows it judges.
- Only mise knows what an install exports, and it answers with `mise bin-paths --json`. A directory scan in VGS would be a second, disagreeing copy of that answer.
- The remainder is reported only when the command answers elsewhere as well. A package's private helper that nothing else provides shadows nothing, and reporting it would train the owner to ignore the notice.
- A hit raises two questions, and one test answers each. Whether it is the install under another name is a question about files; whether the install replaces it is a question about PATH order. Letting a link's name count as owned hid `agy`'s `antigravity` answering ahead of the Antigravity editor's `/usr/bin/antigravity`. Counting the owner's `~/.local/bin/antigravity` as replaced failed every update on the machine this was filed from, though it answers ahead of the package and [D011](D011-mise-owns-agent-harnesses.md) says the owner's wrapper wins.
- `bin_path=` on the registry name is one bracket option and keeps mise's registry the owner of the download URL and the version list. Respelling the whole `http` entry in the catalog would copy a URL template and a version regex that mise already maintains.
- No version is pinned. The overridden entry still installs `latest`, as [D011](D011-mise-owns-agent-harnesses.md) requires.
- The migration asks mise to re-declare rather than reading the config and deciding what has drifted. mise owns what a spec's options mean and where its global config lives; a comparison in VGS would be a second copy of both. An entry mise has not installed is left alone so that an update downloads nothing new.
- Recording an option behind a launcher VGS does not own, or deleting the launcher of an installed entry kept off PATH, takes the command out of every terminal while the run reports success. One judge that every such step asks keeps a new step from deciding it differently, and builds the advice from the cause, so a new cause cannot ship with another cause's remedy.

**Revisit When**: mise's `http` backend can export a named subset of a package directory, which would let an entry publish its own command without the absolute-path launch; or a catalog entry legitimately owns more than one command on PATH, which would move the declared set off the command, `exec` and launch triple.

**Verification**: removing the behaviour behind each rule reddens the case in `scripts/check-dev-tools.py` named for it.

- `test_an_install_may_not_export_a_command_the_entry_does_not_own`, one table row per shape: the declared set (`own`, `closed`, `named`), the answers-elsewhere test (`solo`), the same-install test through a shim (`shimmed`), mise's `latest` directory (`linked`) and a link (`ahead`), walking a declared link's target (`alias`), the shadowing order (`ahead` against `alias`), every copy counting off PATH (`hidden`), the installed-only walk (`absent`), the walk going on past an install mise cannot answer for (`broken` ahead of `open`), and a check mise cannot run failing.
- `test_an_option_the_catalog_changed_reaches_an_earlier_install`: the re-declaration asking the judge, the cause each advice names and the command it ends on, remove-stubs keeping the launcher and failing when mise cannot answer, the conjunction of `mise_sync`'s parts, one read of the installs whose failure is reported once, the exact argv of each re-declaration, and every mise call it makes ending its whole process group on a timeout.
- `test_row_actions_run_and_refuse`: Track and the shared install asking the judge, and the advice each prints.
- `test_the_refreshed_stub_and_the_launch_refusal_reach_the_owner`: the first-launch prompt and Replace with mise each writing the refresh's stub, the stub's empty-root refusal, and `vshell mise refresh` exiting on the outcome.
- `test_update_run_and_count_carry_tools`: `vshell update run tools` exiting on the outcome.
- `test_a_package_kept_off_path_runs_by_absolute_path`: the launcher's reading of `mise where`.
- `test_catalog_is_consistent`: an entry carrying `exec` without an empty `bin_path=`, or the reverse, in any stream it publishes.
