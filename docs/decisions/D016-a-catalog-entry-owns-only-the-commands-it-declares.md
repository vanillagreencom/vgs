# D016: A catalog entry owns only the commands it declares, and an install that exports more stays off PATH

[← Decision Index](INDEX.md)

**Date**: 2026-09-10 **Status**: Active **Research**: — **Refines**: [D011](D011-mise-owns-agent-harnesses.md), [D014](D014-command-provenance-and-duplicates.md)

**Context**: [D014](D014-command-provenance-and-duplicates.md) tests a catalog row against the one command the row declares, and treats two copies of that command as the failure to resolve. A package is not only the command VGS asked for. The Cursor Agent package ships `node`, `rg`, `cursor-askpass` and a dozen more beside its own binary, and mise's registry entry exports the whole package directory. mise's bin path sits ahead of `/usr/bin`, so `node -v` reported the package's 24.5.0 while `/usr/bin/node` was 26.8.1 and `npm` printed a Node-version warning on every invocation, with nothing on the machine saying why. `rg` was replaced the same way. Both replacements reached every process the session started, on every machine that installed the row.

**Decision**: A catalog entry owns the command it declares, the file its `exec` path names inside the package, the executable its launch argv names, and every other name that resolves to one of those files. One file under two names is one install: the `agy` package ships `agy` as a link to `antigravity`, so `antigravity` belongs to the `agy` row. Nothing else the install exports belongs to the entry.

An entry whose package exports more keeps the package's own directory off PATH. Its spec carries an empty mise `bin_path=`, which moves the export from that directory to the install root, and its `exec` field names the file under the root that the stub and the launcher run by absolute path. `mise x` would find no executable of the tool's name inside the package and fall through to PATH, where the stub in `~/.local/bin` answers again. The stub and the launcher both resolve the root with `mise where`, so one install answers both. `bin_path=` alone settles nothing for an archive holding an executable at its top level, since the install root is on PATH; the export check catches that shape.

`mise_sync` in `bin/vshell_mise.py` holds the rule where the spec cannot. `vshell mise refresh` runs it, and so does every `vshell update run tools` after `mise up`. It rewrites the stubs, re-declares options as described below, then asks mise which executables each installed agent, app and tool exports (`mise bin-paths --json`), subtracts what the entry owns, and reports every remainder that also answers somewhere else on PATH. A hit that resolves to the export's own file, as one through mise's `latest` directory does, or to the mise binary, as every mise shim does, is the same install and not a second copy. The declared set comes from the entry; there is no second list and no exemption list.

The check leaves two kinds of install out. An `envs` row installs toolchains with `mise use -g`, and their exports answer ahead of the distribution's because that is what the row is for. A row's `requires` packages are installed globally by the same steps that install the row, and the check does not ask about them: on the machine this was filed from, the Hermes row's `uv` answers ahead of `/usr/bin/uv`. Covering them is separate work, because under the failure rule below a `requires` conflict would fail every update with nothing in the Developer tab that could clear it.

A conflict and a check mise could not answer are both failures. `mise_sync` returns one outcome that passes only when every part passes and carries every part's error, and `vshell update run tools` and `vshell mise refresh` exit non-zero on it. The Cursor row shipped with nothing reporting the shadowing, and a notice above a passing exit would leave a supervisor reading the exit code no better off. No install path runs the check: the first-launch prompt, the Replace with mise action and a stub's own first run all leave it to the next refresh or tools update.

mise copies a spec's backend options into the global config the first time a tool is used and never revisits them: `mise up` moves the version and leaves the options as recorded. `mise_sync` re-declares an installed entry whose spec carries options in the same step that writes its stub, and only then. An option can take the package off PATH, which leaves the launcher the only way in from a shell. An entry whose launcher VGS did not write, because auto-install is off or the file is the owner's own, therefore keeps its recorded options, and when it still exports a conflict the check names the launcher and the way out: let VGS write it, or make the owner's launcher run the binary by absolute path and declare the spec with `mise use -g`. A spec carrying no option is not re-declared, yet mise may hold options for it from its registry: the Cursor row's plain spec recorded `bin_path = "dist-package"`. A change that removes an option from a row's spec therefore carries its own re-declaration.

**Rationale**:

- The declaration already exists. `command`, the `exec` file and the launch argv's executable are what the catalog says an entry is for, so the rule needs no new vocabulary and cannot drift from the rows it judges.
- Only mise knows what an install exports, and it answers with `mise bin-paths --json`. A directory scan in VGS would be a second, disagreeing copy of that answer.
- The remainder is reported only when the command answers elsewhere as well. A package's private helper that nothing else provides shadows nothing, and reporting it would train the owner to ignore the notice.
- Judging every name by the file it resolves to answers a link inside the package, mise's `latest` directory and mise's shims with one rule. Comparing names counted `agy`'s `antigravity` as a second copy of the owner's own wrapper for the same install, failed every update on the machine this was filed from, and left deleting that wrapper as the only remedy, though [D011](D011-mise-owns-agent-harnesses.md) says the owner's wrapper wins.
- `bin_path=` on the registry name is one bracket option and keeps mise's registry the owner of the download URL and the version list. Respelling the whole `http` entry in the catalog would copy a URL template and a version regex that mise already maintains.
- No version is pinned. The overridden entry still installs `latest`, as [D011](D011-mise-owns-agent-harnesses.md) requires.
- The migration asks mise to re-declare rather than reading the config and deciding what has drifted. mise owns what a spec's options mean and where its global config lives; a comparison in VGS would be a second copy of both. An entry mise has not installed is left alone so that an update downloads nothing new.
- The re-declaration and the launcher are one decision. Re-declaring where VGS writes no launcher takes the command out of every terminal while the run reports success.

**Revisit When**: mise's `http` backend can export a named subset of a package directory, which would let an entry publish its own command without the absolute-path launch; a catalog entry legitimately owns more than one command on PATH, which would move the declared set off the command, `exec` and launch triple; or a package exports a system command's name as a link to its own binary, which the resolved-file rule reads as owned.

**Verification**: `test_an_install_may_not_export_a_command_the_entry_does_not_own`, `test_a_package_kept_off_path_runs_by_absolute_path`, `test_the_refreshed_stub_and_the_launch_refusal_reach_the_owner` and `test_an_option_the_catalog_changed_reaches_an_earlier_install` in `scripts/check-dev-tools.py`. The export case is table-driven over an undeclared export that shadows a distribution command, a declared one, an undeclared one nothing else provides, one visible only through a mise shim, the file `exec` names, the executable the launch argv names, one reported through mise's `latest` directory, a declared name that links to an undeclared one, an install mise cannot answer for ahead of a conflicting one, and an install mise does not hold. The stub case writes the stub through the refresh and through the shared install, compares the two, and runs it against a stand-in `mise` that names a root and one that names none. The options case runs `mise_sync` with the owner's launcher, with auto-install off, with VGS's launcher and a refused declaration, and with every declaration accepted. Each rule reddens its case when its behaviour is removed: the declared-set subtraction, ownership by resolved file, the answers-elsewhere test, the shim rule, the `latest` resolution, the installed-only skip, continuing past an install mise cannot answer for, the failing outcome, the conjunction of `mise_sync`'s parts, both entry points exiting on that outcome, re-declaring only where VGS wrote the launcher, the way-out line, the stub the shared install writes, the stub's empty-root refusal, and the launcher's reading of `mise where`. `test_catalog_is_consistent` fails an entry carrying `exec` without an empty `bin_path=`, or the reverse, in every stream it publishes.
