# D016: A catalog entry owns only the commands it declares, and an install that exports more stays off PATH

[← Decision Index](INDEX.md)

**Date**: 2026-09-10 **Status**: Active **Research**: — **Refines**: [D011](D011-mise-owns-agent-harnesses.md), [D014](D014-command-provenance-and-duplicates.md)

**Context**: [D014](D014-command-provenance-and-duplicates.md) tests a catalog row against the one command the row declares, and treats two copies of that command as the failure to resolve. A package is not only the command VGS asked for. The Cursor Agent package ships `node`, `rg`, `cursor-askpass` and a dozen more beside its own binary, and mise's registry entry exports the whole package directory. mise's bin path sits ahead of `/usr/bin`, so `node -v` reported the package's 24.5.0 while `/usr/bin/node` was 26.8.1 and `npm` printed a Node-version warning on every invocation, with nothing on the machine saying why. `rg` was replaced the same way. Both replacements reached every process the session started, on every machine that installed the row.

**Decision**: A catalog entry owns the command it declares, the file its `exec` path names inside the package, and the executable its launch argv names. Nothing else the install exports belongs to the entry, another name for one of those files included: the `agy` package ships `agy` as a link to `antigravity`, and `antigravity` is judged like any other export.

An entry whose package exports more carries an `exec` path, and VGS installs it with an empty mise `bin_path=`, which moves the export from the package directory to the install root. The stub and the launcher run the `exec` file by absolute path under the root `mise where` names. `mise x` would find no executable of the tool's name inside the package and fall through to PATH, where the stub answers again. The row keeps the plain spec. `vshell update run all` can upgrade VGS while the previous release runs it, and that release writes the stubs from the new catalog with code that knows no `exec`; from the plain spec it writes the launcher it always wrote. `bin_path=` alone settles nothing for an archive holding an executable at its top level, since the install root is on PATH; the export check catches that shape.

`vshell mise refresh` runs `mise_sync` in `bin/vshell_mise.py`. Every `vshell update run tools` runs that command as its own process after `mise up`, so the code comes from the release whose catalog it reads. `mise_sync` settles every launcher, as described below, then asks mise which executables each installed agent, app and tool exports (`mise bin-paths --json`) and walks PATH for every exported name the entry does not declare. `command_on_path_elsewhere` reads PATH the way the owner's shells order it: each directory at its first place only, and `~/.local/bin` ahead of all of them, as the stub writer takes it to be, so no install replaces a copy there. A hit that resolves to one of the install's own files or to the mise binary is the install under another name, as a link inside the package, mise's `latest` directory and every mise shim are, and is passed over. So is every hit ahead of the install's first answer. The first hit left is a conflict. Where the install answers nowhere on that PATH, as under the shell service's, every other copy counts. The declared set comes from the entry; there is no second list and no exemption list.

The check leaves two kinds of install out. An `envs` row installs toolchains with `mise use -g`, and their exports answer ahead of the distribution's because that is what the row is for. A row's `requires` packages are installed globally by the same steps that install the row, and the check does not ask about them: on the machine this was filed from, the Hermes row's `uv` answers ahead of `/usr/bin/uv`. Covering them is separate work, because under the failure rule below a `requires` conflict would fail every update with nothing in the Developer tab that could clear it.

A conflict and a check mise could not answer are both failures. `mise_sync` passes only when every part passes and carries every part's error, and `vshell mise refresh` exits non-zero on it, which fails the tools update. The Cursor row shipped with nothing reporting the shadowing, and a notice above a passing exit would leave a supervisor reading the exit code no better off. No install path runs the check: the first-launch prompt, Replace with mise and a stub's own first run leave it to the next refresh.

Once an entry with an `exec` path has its options recorded, its launcher is the only way to run its command from a shell. One step, `mise_settle`, keeps that launcher working after every action that changes it, so no action judges it for itself. The step rewrites every stub VGS wrote from the current template, auto-install on or off, and writes the launcher of every installed `exec` entry that has none, whatever the setting, unless another copy of its command answers on PATH, which the launcher would hide. The install itself is no other copy. `install_exports` gives the export check and the launcher one set of the install's files and the mise binary, so the install's old export, which a mise-activated PATH carries until the re-declaration takes it off, and every mise shim are passed over. Every other copy counts wherever it sits on PATH, because `~/.local/bin` answers ahead of all of them. mise copies a spec's backend options into the global config the first time the spec is used, and `mise up` keeps them, so the step then re-declares an installed `exec` entry's spec, and only behind the stub it has just written. That is how the Cursor row's option reaches an install made before it. The refresh, Track, the install the first-launch prompt and Replace with mise share, and `vshell mise remove-stubs` each end with the step, and `vshell mise opt-in` and a channel pick run the refresh and fail as it does. remove-stubs keeps the launcher of every installed `exec` entry. When mise cannot say what is installed, it keeps every `exec` entry's stub and fails.

Two states leave the step no launcher to write. The first is the owner's own file at the launcher path, which VGS never replaces. `launcher_refusal` detects it before anything records the options or removes a package: Track and Replace with mise refuse, and the refresh records nothing. The second is another copy of the command where no launcher exists; a launcher VGS already wrote is rewritten and answers ahead of that copy. Track and Replace with mise go ahead behind it, because that copy still answers once the package is off PATH, and Replace removes a distribution's copy first. While the install still shadows a copy, the refresh prints the advice for its state. For the owner's file: make it run the binary by absolute path, then run `mise use -g '<spec>'`. For another copy, the advice names where the command answers: remove that copy and run the refresh, or keep it and run `mise use -g '<spec>'`, which leaves that copy as the command.

**Rationale**:

- The declaration already exists. `command`, the `exec` file and the launch argv's executable are what the catalog says an entry is for, so the rule needs no new vocabulary and cannot drift from the rows it judges.
- Only mise knows what an install exports, and it answers with `mise bin-paths --json`. A directory scan in VGS would be a second, disagreeing copy of that answer.
- The remainder is reported only when the command answers elsewhere as well. A package's private helper that nothing else provides shadows nothing, and reporting it would train the owner to ignore the notice.
- A hit raises two questions. Whether it is the install under another name is a question about files; whether the install replaces it is a question about PATH order. Letting a link's name count as owned hid `agy`'s `antigravity` answering ahead of the Antigravity editor's `/usr/bin/antigravity`. Reading PATH as the check's process inherits it counted the owner's `~/.local/bin/antigravity` as replaced, both from a terminal whose PATH lists that directory twice and from the shell service, whose PATH carries no mise directory. Every update failed on the machine this was filed from, though [D011](D011-mise-owns-agent-harnesses.md) says the owner's wrapper wins.
- `bin_path=` on the registry name is one bracket option and keeps mise's registry the owner of the download URL and the version list. Respelling the whole `http` entry in the catalog would copy a URL template and a version regex that mise already maintains.
- No version is pinned. The overridden entry still installs `latest`, as [D011](D011-mise-owns-agent-harnesses.md) requires.
- The migration asks mise to re-declare rather than reading the config and deciding what has drifted. mise owns what a spec's options mean and where its global config lives; a comparison in VGS would be a second copy of both. An entry mise has not installed is left alone so that an update downloads nothing new.
- A judge in front of each action answered a proxy: it counted any file carrying VGS's marker as a working launcher, and main's Cursor stub carries the marker and runs `mise x` on the plain spec. One step that every action ends with keeps the launcher current instead, which leaves two states it cannot change, each with its advice.
- A process started before a package upgrade runs the old release's code against the new release's files. The catalog therefore stays readable by the previous release, and the tools update runs the refresh as a new process.

**Revisit When**: mise's `http` backend can export a named subset of a package directory, which would let an entry publish its own command without the absolute-path launch; or a catalog entry legitimately owns more than one command on PATH, which would move the declared set off the command, `exec` and launch triple.

**Verification**: removing the behaviour behind each rule below reddens the case in `scripts/check-dev-tools.py` named for it.

- `test_an_install_may_not_export_a_command_the_entry_does_not_own`, one table row per shape: the declared set (`own`, `closed`, `named`), the answers-elsewhere test (`solo`), the same-install test through a shim (`shimmed`), mise's `latest` directory (`linked`) and a link inside the package (`alias`), with mise and a linked `node` in the stand-in `/usr/bin` (`open`, `alias`), each PATH directory at its first place and in order (`ahead`), `~/.local/bin` ahead of every install and every other copy counting off PATH (`hidden`), the installed-only walk (`absent`), the walk going on past an install mise cannot answer for (`broken` ahead of `open`), and a check mise cannot run, or answers in a shape it never prints, failing.
- `test_every_launcher_is_settled_before_its_option_is_recorded`, one row per state: VGS's stubs rewritten with auto-install off, the `exec` entry's option recorded only behind the one just written, with the `bin_path=` spec and exact argv, and never for an entry without `exec`, a missing launcher written for an installed `exec` entry while only its own export and a shim answer, nothing recorded behind the owner's own file or behind another copy that answers ahead of the install, the advice for each printed only while its install shadows a copy and naming where the other copy answers, a failed re-declaration and a conflict each failing `vshell mise refresh`, and the failed re-declaration failing `vshell mise opt-in` and a channel pick, one read of the installs, remove-stubs ending with the step and never removing an installed `exec` entry's launcher, and keeping every `exec` stub, and failing, when mise cannot say what is installed, and every mise call ending its whole process group on a timeout.
- `test_row_actions_run_and_refuse`: Track and Replace with mise refusing behind the owner's own launcher before any mise command or removal, Track going ahead behind another copy and behind a file at the launcher path of an entry without `exec`, and Track and the shared install ending with the step. `test_first_launch_asks_before_installing`: the first-launch prompt ending with it.
- `test_an_exec_stub_runs_the_file_under_the_install_root`: the stub running the `exec` file, its empty-root refusal, and the stub a release without `exec` writes from the row running `mise x` on a spec with no options.
- `test_a_package_kept_off_path_runs_by_absolute_path`: the launcher's reading of `mise where` for the `bin_path=` spec, and a launch mise names no root for exiting 1 with the reason.
- `test_outdated_parsing_and_update_steps` and `test_update_run_and_count_carry_tools`: the refresh running as its own process after `mise up`, and a failing refresh failing the update.
