# Plugin manager

Covers: bin/vgsh-plugin-judge, scripts/test-vgsh-outdated.sh, scripts/test-vgsh-prompts.sh, scripts/test-vgsh-plugin-settings.sh

How plugins are discovered, enabled, disabled, placed in the bar, installed, updated, checked for updates and removed, and what the manager's user interface may do. The plugin contract itself is [plugins.md](plugins.md), and the Settings window, the manager's user interface, is [settings-window.md](settings-window.md).

## Mechanism

The manager is core: `Registry` lists and judges, `Plugins` enables, disables, places widgets and writes settings and keys, and `vgsh plugin` installs. Its user interface is a plugin, `vgs.settings` ("Settings"), which reaches the manager through the `manager` capability, [D032](../decisions/D032-settings-plugin-and-manifest-settings-convention.md). Settings lists itself, so it is disabled, rebound and deep-linked like any plugin; with it disabled, `vgsh plugin` and the IPC still manage every plugin.

- The capability hands over `Registry.managerRows`, one row per discovered plugin: the listing metadata, its icon (`PluginLogic.pluginIcon`), kinds, capabilities, `source` (`bundled` under the shell's plugins directory, `installed` under the user's), enabled state, `placed` ([placement.md](placement.md)), schema, the settings it receives, `status` (`PluginLogic.statusRows`: each status entry the Settings page draws, with the value the plugin published or `unreported`, [status.md](status.md)), `secretLabel` (the manifest's `secrets` label or "", which the Settings page's Connect field asks for), `binds` (`PluginLogic.bindRows`: each shortcut with the key in effect, the manifest's key and the description the plugin registered), `requirements` (`PluginLogic.requirementRows`: each declared command with its state from the last scan, [requirements.md](requirements.md)) and `errors`: each failed build of one of its kinds, once per cause, then each problem the Hyprland layer reports for it. The Hyprland layer hands its problems to the registry once; `listPlugins` reads them there too.
- `setEnabled` calls the same `Plugins.setEnabled` the IPC does, and `setPlaced(id, placed)` the same `Plugins.setPlaced` the IPC `setPluginPlaced` does. `setSetting` writes a setting to every entry the plugin's instances read. `setKey(id, shortcut, key)` writes the plugin's `plugins[].keys` entry: a key string rebinds, `null` unbinds, `undefined` removes the entry so the manifest's key applies; `PluginLogic.keyRefusal` and `PluginLogic.withKey` decide it. A disabled plugin's setting or key is refused, since listing a third-party row would enable it. Each reply is the IPC's keyed line.
- `update(id)`, `remove(id)` and `add()` run no command in the shell: each opens a core floating TUI ([tui-capability.md § The capability](tui-capability.md#the-capability)), so every question the command asks stays a question on a terminal the user sees ([D007](../decisions/D007-install-runs-no-plugin-code.md)). `update` opens `vgsh plugin update <id>`, with no `--yes`, and `remove` opens `vgsh plugin remove <id>`, each for an installed plugin; `add` opens `core/plugin-add`, `vgsh plugin add` with no URL, which asks for one with gum input and ends with the requirement report. `PluginLogic.managerTui` picks the row; an id no plugin has answers `unknown: <id>` and a bundled plugin's update or remove `refused: bundled=<id>`. Otherwise each answers `ok` when the launcher started, and when the TUI's key was busy, since the runner then asks the compositor to focus the live run's window. `PluginLogic.tuiShownAnswer` makes that answer; any other refusal of `shell.tui.open`'s, such as `refused: tui=core/<name> reason=launcher-missing`, passes through. The command asks a running shell to rescan when it changes a plugin or a package, and the rows follow.
- `act(id, key)`, `storeSecret(id, key, account, secret, done)` and `clearSecret(id, key, account, done)` run a plugin's declared setup steps from its Settings page: an entry's action while its value offers it, and a listed account's Connect and Disconnect through the core's one secret writer. Their judges and answers: [status-actions.md § Actions and secrets](status-actions.md#actions-and-secrets).
- `installRequirements(id)` raises the requirement notice for any plugin with every missing command, the optional ones included, and the notice's Install runs the packages in the core TUI `core/requirements-install` ([requirement-notice.md](requirement-notice.md)). It answers `ok` once the notice holds the plugin, `unknown: <id>`, `refused: requirements=<id> reason=satisfied` when nothing is missing, or the queue's `refused: notices=full limit=<n>`.
- Enable and disable go through the shell's IPC, which writes the user file; the shell watches the file and re-derives the enabled set.
- Disable lists the id in `disabledPlugins` and changes nothing else: placement, settings rows and the active bar id stay, so re-enabling restores the exact screen. Enable unlists the id and gives a plugin a presence only when it has none: a bar becomes the active bar, an unplaced widget is placed in its default section, an unlisted third-party plugin of another kind is listed. Enabling a plugin that already has its presence is idempotent. `scripts/test-plugin-logic.js` pins each rule.
- Placement is apart from enablement: `setPlaced` shows or hides a widget in the bar and never changes `disabledPlugins`, [placement.md](placement.md).
- The configuration files, their shape, their states and the write rule: [configuration.md](configuration.md). Nothing is built before the first scan and before the configuration is ready.
- `vgsh plugin list` prints every discovered plugin with its enabled state, each manifest error, each id collision, each configured id no plugin has ([configuration.md § Unknown ids](configuration.md#unknown-ids)) and each missing requirement with this system's package ([requirements.md § Reports](requirements.md#reports)). `bin/vgsh-plugin-judge list` formats the lines from the `listPlugins` reply.
- `vgsh plugin settings <id>` prints, as one JSON line, the settings the plugin under that id hands its service, panel and floating TUIs: `PluginLogic.settingsFor` its `plugins[]` row, over the shipped and user files `PluginLogic.effectiveConfig` merges. A floating TUI reads its plugin's settings through it, since `shell.tui.open` hands a script no arguments. A value the schema refuses, as a hand edit can leave, is refused as `setting=<key> want=<type> id=<id>`, and an id no accepted manifest names as `unknown=<id>`. It needs no running shell and changes nothing. `scripts/test-vgsh-plugin-settings.sh` pins each answer, with judge copies that ignore the user file and skip the schema as controls.
- Only the shell the runner started accepts a state-changing call; [runtime.md § Process](runtime.md#process).
- `add` clones into a staging directory beside `~/.config/vgs/plugins/`, runs the manifest judge, refuses an id another plugin owns or an occupied target, lists the id in `disabledPlugins` when the configuration would already enable it, then moves it into place. `add` with no URL asks for one with gum input on a terminal and refuses with `url=missing`, exit 2, without one. `update` refuses a modified checkout, prints the incoming diff, then asks `vgsh: update <id>? [y/N]` on stderr and fast-forwards only on `y` or `yes`; it rolls back a version the judge refuses. The question is the review step before new plugin code runs, since a rescan builds it at once. `remove` deletes only `~/.config/vgs/plugins/<id>` holding that id, never a bundled plugin or a symlink, and asks `vgsh: remove <id>? [y/N]` first. For either question any other answer refuses as `declined=<id>`, and with no terminal on stdin the command refuses as `no-terminal=<id>` unless `--yes` gives the answer; each refusal leaves the plugin as it was. None runs plugin code or a git hook; each that changes the plugin directory starts a rescan of a running shell. `bin/vgsh-plugin-judge` makes their decisions through `PluginLogic.js`, `scripts/test-vgsh.sh` pins each rule and `scripts/test-vgsh-prompts.sh` each question on a terminal, [D007](../decisions/D007-install-runs-no-plugin-code.md).
- `add` then reports the new plugin's missing requirements: one `requires <command> (<package>)` line each and the `vgsh pkg run install` commands that install their packages. On a terminal it asks `Install now? [y/N]` and runs them on `y`; without one it leaves them printed. Each run asks a running shell to rescan, so the manager's rows show the installed commands present. `vgsh plugin requirements <id>` reports one plugin's requirements and `vgsh doctor` the core's and every enabled plugin's, each with its state and this system's package: [requirements.md § Command line](requirements.md#command-line).

Manager rows also carry `settingChoices`, the per-setting Select models from `PluginLogic.settingChoices`. The same accepted status values feed those models and the status rows. [status.md § Setting choices](status.md#setting-choices) holds the contract.

## Outdated

`vgsh plugin outdated [--json]` and `vgsh theme outdated [--json]` report how far each installed git checkout is behind its upstream. They are read-only. An Updates plugin composes both `--json` forms, so the rows below are a contract.

- **Rows.** `plugin outdated` has one row for each directory or symlink under `~/.config/vgs/plugins/`, with the directory name as its `id`. `theme outdated` has one row for each installed package under `~/.config/vgs/themes/`, as `bin/vgsh-theme-judge checkouts` lists them. Bundled plugins and shipped packages are no checkouts and have no row. Each row is resolved as `update` resolves its id or name, so a symlink, a directory whose manifest names another id and a package `theme update` refuses are error rows. A catalog install is no checkout; its row compares digests: [theme-catalog.md § Install](theme-catalog.md#install).
- **Probe.** Each checkout must be its own checkout. `git fetch` then runs with hooks and the filesystem monitor off, no submodules, no `FETCH_HEAD`, no auto maintenance, under `timeout 10` with SIGKILL 5 s after its TERM, in a session of its own with no controlling terminal. Its environment asks nobody: `GIT_TERMINAL_PROMPT=0` ends git's terminal prompt, an empty `GIT_ASKPASS` outranks `core.askPass` and `SSH_ASKPASS` so git runs no askpass, `SSH_ASKPASS_REQUIRE=never` keeps ssh from one, and `GCM_INTERACTIVE=false` makes Git Credential Manager fail instead of asking. A key the agent holds, a key without a passphrase and a stored credential still answer, and the user's ssh command and configuration stay as they are; anything else that needs a person is a failed fetch. The fetch updates the remote-tracking refs and their objects. `head` is `HEAD` and `upstream` is `@{upstream}`, each a full commit id; a catalog install's are 64-digit package digests. `behind` is `git rev-list --count HEAD..@{upstream}`: the commits upstream has and `HEAD` lacks. It does not say whether `update` can fast-forward, because `update` refuses a rewritten history itself.
- **JSON.** One line: an array of `{ id, behind, head, upstream, error }` sorted by `id`, and `[]` when nothing is installed. On success `error` is null. On a failure `behind`, `head` and `upstream` are null, and `error` is the keyed line `update` prints for the same cause, without `vgsh: refused: `. Examples: `fetch=<id>`, `upstream=missing path=<dir>`, `not-a-checkout=<dir>`, `symlink=<path>`, `theme=<name> reason=symlink path=<dir>`. A fetch the timeout ends is `fetch=<id> timeout=10s`.
- **Text.** One line per row: `<id> behind=<n> head=<commit> upstream=<commit>` with 12-digit commits, or `<id> error=<refusal>`. Nothing installed prints no line. The text form is for people and the JSON form for programs.
- **Exit.** 0 whenever the report prints, error rows included. 1 when the plugin directory or the themes directory cannot be read: `unreadable=<dir>`, or `themes=unreadable path=<dir> error=<code>`. 2 on a bad invocation. 75 from `theme outdated` when another theme command holds the lock: `outdated=themes reason=busy`. Git's own messages pass through on stderr.
- **Stop.** SIGTERM, SIGINT or SIGHUP sent to the verb's process group, as the Updates check stops a probe, misses the fetch's own session. The verb traps it, sends TERM to that session, waits until git has ended and exits 128 plus the signal's number, printing no report. A fetch that ignores TERM gets SIGKILL 5 s later. `vgsh self status` stops its fetch or its `ls-remote` of `main` the same way.
- **Never.** No merge, reset or checkout. The fetch's update of remote-tracking refs is the only write. No plugin or package code runs, no git hook runs, and neither git nor ssh prompts on a terminal or opens an askpass dialog. `plugin outdated` takes no theme lock. `theme outdated` holds the theme lock shared for the whole run: a second `theme outdated` runs beside it, and apply, follow, reload, background, add, update and remove are refused busy until it ends. No git process of a row holds the lock's descriptor.
- **Omarchy.** `omarchy-update-available` (basecamp/omarchy `main`, e332dc9, read 2026-09-28) runs `GIT_TERMINAL_PROMPT=0 timeout 10 git fetch --quiet` in a dev checkout and counts `git rev-list --count HEAD..<upstream>`. VGS takes the prompt setting, the 10 s bound and the count. It differs in five ways. It reports one JSON row per checkout, not one text line. A failed or timed-out fetch and a missing upstream are `error` rows, where Omarchy continues with `|| true`, counts against the stale ref and skips a checkout with no upstream. Hooks are off, as for every vgsh git call. The fetch writes no `FETCH_HEAD` and starts no maintenance. Omarchy stops only git's terminal prompt, so an askpass, a credential manager or ssh on the terminal can still ask; VGS stops each.

## Invariants

1. `plugin outdated` and `theme outdated` count the commits of a local bare upstream that the checkout lacks. They report zero for a current checkout, and an error row for an unreachable remote, a missing upstream, a directory that is no checkout, a symlink, a missing manifest and a fetch past the timeout. They leave `HEAD`, the work tree and `FETCH_HEAD` unchanged, run no git hook, hand ssh `GIT_TERMINAL_PROMPT=0`, `SSH_ASKPASS_REQUIRE=never` and no terminal even when run on one, run no askpass for git's credential prompt and hand the credential helper `GCM_INTERACTIVE=false`, and keep the lock's descriptor from git. `theme outdated` is refused busy under an exclusive hold of the theme lock and runs under a shared one. Enforced by `scripts/test-vgsh-outdated.sh`. Its controls are copies of `bin/vgsh` that keep hooks, pull instead of fetching, write `FETCH_HEAD`, drop the timeout, any one of the four prompt settings, the fetch's own session or the descriptor close, take no lock or an exclusive one, or list an unreadable directory as empty.
2. A SIGTERM, SIGINT or SIGHUP to `plugin outdated`'s process group during a fetch ends the fetch, and the verb exits 128 plus the signal's number only after the fetch has ended, with no report; a fetch that ignores TERM ends by SIGKILL after the grace. `self status` stops its fetch and its `ls-remote` the same way. Unstopped, a fetch that the grace's SIGKILL ends after its timeout is still a `timeout=10s` row. Enforced by `scripts/test-vgsh-outdated.sh` and `scripts/test-vgsh-self.sh` with a stand-in git. The controls are copies of `bin/vgsh` without the fetch's trap, whose fetch outlives the verb, without the step's trap, which returns before the fetch has ended, without the kill grace, which waits out a fetch that ignores TERM, and one that reads that SIGKILL as a plain failure.
