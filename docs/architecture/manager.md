# Plugin manager

Covers: bin/vgsh-plugin-judge, shell/plugins/vgs.settings/**, scripts/smoke/rows/manager.sh, scripts/smoke/rows/settings.sh, scripts/test-vgsh-outdated.sh

How plugins are discovered, enabled, disabled, installed, updated, checked for updates and removed, and what the manager's user interface may do. The plugin contract itself is [plugins.md](plugins.md).

## Mechanism

The manager is core: `Registry` lists and judges, `Plugins` enables, disables and writes settings and keys, and `vgsh plugin` installs. Its user interface is a plugin, `vgs.settings` ("Settings"), which reaches the manager through the `manager` capability, [D032](../decisions/D032-settings-plugin-and-manifest-settings-convention.md). Settings lists itself, so it is disabled, rebound and deep-linked like any plugin; with it disabled, `vgsh plugin` and the IPC still manage every plugin.

- The capability hands over `Registry.managerRows`, one row per discovered plugin: the listing metadata, its icon (`PluginLogic.pluginIcon`), kinds, capabilities, `source` (`bundled` under the shell's plugins directory, `installed` under the user's), enabled state, schema, the settings it receives, `binds` (`PluginLogic.bindRows`: each shortcut with the key in effect, the manifest's key and the description the plugin registered), `requirements` (`PluginLogic.requirementRows`: each declared command with its state from the last scan, [requirements.md](requirements.md)) and `errors`: each failed build of one of its kinds, once per cause, then each problem the Hyprland layer reports for it. The Hyprland layer hands its problems to the registry once; `listPlugins` reads them there too.
- `setEnabled` calls the same `Plugins.setEnabled` the IPC does. `setSetting` writes a setting to every entry the plugin's instances read. `setKey(id, shortcut, key)` writes the plugin's `plugins[].keys` entry: a key string rebinds, `null` unbinds, `undefined` removes the entry so the manifest's key applies; `PluginLogic.keyRefusal` and `PluginLogic.withKey` decide it. A disabled plugin's setting or key is refused, since listing a third-party row would enable it. Each reply is the IPC's keyed line.
- Enable and disable go through the shell's IPC, which writes the user file; the shell watches the file and re-derives the enabled set.
- Disable lists the id in `disabledPlugins` and changes nothing else: placement, settings rows and the active bar id stay, so re-enabling restores the exact screen. Enable unlists the id and gives a plugin a presence only when it has none: a bar becomes the active bar, an unplaced widget is placed in its default section, an unlisted third-party plugin of another kind is listed. Enabling a plugin that already has its presence is idempotent. `scripts/test-plugin-logic.js` pins each rule.
- The configuration files, their shape, their states and the write rule: [configuration.md](configuration.md). Nothing is built before the first scan and before the configuration is ready.
- `vgsh plugin list` prints every discovered plugin with its enabled state, each manifest error, each id collision, each configured id no plugin has ([configuration.md § Unknown ids](configuration.md#unknown-ids)) and each missing requirement with this system's package ([requirements.md § Reports](requirements.md#reports)). `bin/vgsh-plugin-judge list` formats the lines from the `listPlugins` reply.
- Only the shell the runner started accepts a state-changing call; [runtime.md § Process](runtime.md#process).
- `add` clones into a staging directory beside `~/.config/vgs/plugins/`, runs the manifest judge, refuses an id another plugin owns or an occupied target, lists the id in `disabledPlugins` when the configuration would already enable it, then moves it into place. `update` refuses a modified checkout, prints the incoming diff, then asks `vgsh: update <id>? [y/N]` on stderr and fast-forwards only on `y` or `yes`; it rolls back a version the judge refuses. Any other answer refuses as `declined=<id>`, and with no terminal on stdin update refuses as `no-terminal=<id>` unless `vgsh plugin update --yes <id>` gives the answer; both leave the checkout at its old commit. The question is the review step before new plugin code runs, since a rescan builds it at once. `remove` deletes only `~/.config/vgs/plugins/<id>` holding that id, never a bundled plugin or a symlink. None runs plugin code or a git hook; each that changes the plugin directory starts a rescan of a running shell. `bin/vgsh-plugin-judge` makes their decisions through `PluginLogic.js`, and `scripts/test-vgsh.sh` pins each rule, [D007](../decisions/D007-install-runs-no-plugin-code.md). The Settings page of an installed plugin shows its `update` and `remove` commands; it runs neither.

## Outdated

`vgsh plugin outdated [--json]` and `vgsh theme outdated [--json]` report how far each installed git checkout is behind its upstream. They are read-only. An Updates plugin composes both `--json` forms, so the rows below are a contract.

- **Rows.** `plugin outdated` has one row for each directory or symlink under `~/.config/vgs/plugins/`, with the directory name as its `id`. `theme outdated` has one row for each installed package under `~/.config/vgs/themes/`, as `bin/vgsh-theme-judge checkouts` lists them. Bundled plugins and shipped packages are no checkouts and have no row. Each row is resolved as `update` resolves its id or name, so a symlink, a directory whose manifest names another id and a package `theme update` refuses are error rows.
- **Probe.** Each checkout must be its own checkout. `git fetch` then runs with hooks and the filesystem monitor off, `GIT_TERMINAL_PROMPT=0`, no submodules, no `FETCH_HEAD`, no auto maintenance, under `timeout 10`. The fetch updates the remote-tracking refs and their objects. `head` is `HEAD` and `upstream` is `@{upstream}`, each a full commit id. `behind` is `git rev-list --count HEAD..@{upstream}`: the commits upstream has and `HEAD` lacks. It does not say whether `update` can fast-forward, because `update` refuses a rewritten history itself.
- **JSON.** One line: an array of `{ id, behind, head, upstream, error }` sorted by `id`, and `[]` when nothing is installed. On success `error` is null. On a failure `behind`, `head` and `upstream` are null, and `error` is the keyed line `update` prints for the same cause, without `vgsh: refused: `. Examples: `fetch=<id>`, `upstream=missing path=<dir>`, `not-a-checkout=<dir>`, `symlink=<path>`, `theme=<name> reason=symlink path=<dir>`. A fetch the timeout ends is `fetch=<id> timeout=10s`.
- **Text.** One line per row: `<id> behind=<n> head=<commit> upstream=<commit>` with 12-digit commits, or `<id> error=<refusal>`. Nothing installed prints no line. The text form is for people and the JSON form for programs.
- **Exit.** 0 whenever the report prints, error rows included. 1 when the plugin directory or the themes directory cannot be read: `unreadable=<dir>`, or `themes=unreadable path=<dir> error=<code>`. 2 on a bad invocation. 75 from `theme outdated` when another theme command holds the lock: `outdated=themes reason=busy`. Git's own messages pass through on stderr.
- **Never.** No merge, reset or checkout. The fetch's update of remote-tracking refs is the only write. No plugin or package code runs, no git hook runs and git never prompts. `plugin outdated` takes no theme lock. `theme outdated` holds the theme lock shared for the whole run: a second `theme outdated` runs beside it, and apply, follow, reload, background, add, update and remove are refused busy until it ends. No git process of a row holds the lock's descriptor.
- **Catalog.** A package the theme catalog installs (roadmap D038) is no git checkout and will carry the catalog marker. The catalog work reports it through that marker and drops it from `checkouts`. Until that work lands, every installed package is a row.
- **Omarchy.** `omarchy-update-available` (basecamp/omarchy `main`, e332dc9, read 2026-09-28) runs `GIT_TERMINAL_PROMPT=0 timeout 10 git fetch --quiet` in a dev checkout and counts `git rev-list --count HEAD..<upstream>`. VGS takes the prompt setting, the 10 s bound and the count. It differs in four ways. It reports one JSON row per checkout, not one text line. A failed or timed-out fetch and a missing upstream are `error` rows, where Omarchy continues with `|| true`, counts against the stale ref and skips a checkout with no upstream. Hooks are off, as for every vgsh git call. The fetch writes no `FETCH_HEAD` and starts no maintenance.

## The Settings window

- **Surface.** An unanchored `panel` summon, which the panel host builds as a layer surface on the top layer, with keyboard focus on demand, when summoned and destroys on hide. `center` placement ignores reserved space, so the window is centred on the whole monitor. It is `min(size.window.width, screen width − 2 × size.window.gutter)` wide and `size.window.heightShare` of the screen's height tall, read from its `screens` capability. The gear widget summons it on its own screen; the `toggle` shortcut, `SUPER+M` in the manifest, and the IPC summon it on the focused monitor.
- **Pages.** The list page holds a search field and one row per manager row; the plugin page holds a back button and the plugin's name as a `TitleButton` whose `Menu` lists every plugin, the current one checked, and jumps to another's page. A push or pop slides on `motion.duration.normal`, so a `motion.scale` of 0 makes it instant. Escape pops the page, then hides the window.
- **Fields.** One `SettingField` per schema entry, in the manifest's key order, entries without a `group` first and each group under a `SectionHeader` in the order its first entry appears: a `Switch` for a boolean, a `Select` for an enum, a `Slider` with its value for a number with `min` and `max`, and a `TextField` otherwise. One `KeyField` per bind. A field shows what the configuration holds after every write, so a refused value leaves the old one in place, and the refusal stays on the page until a later call for that plugin succeeds.
- **Payload.** `{}` opens the list and `{"plugin":"<id>"}` that plugin's page, through `vgsh ipc call shell summon panel vgs.settings '<payload>'` or the plugin's own `open` IPC; the `surfaces` capability opens only its caller's surfaces, so another plugin links to a page through that command; an id no plugin has opens the list with a notice naming it, and any other key or a payload that is no object throws out of `open()`, which refuses the summon.
- **Layout.** The list's heading, search field and rows share one left and one right edge, clear of the scroll bar's gutter whether the list overflows or not, and each row's lines centre on its icon. On a page, every inline label starts `row.paddingX` in from the column, every control `field.labelWidth` plus `field.labelGap` past that edge and ends `row.paddingX` from the column's right, and each label centres on its control or value. `scripts/smoke/rows/manager.sh` reads both pages back through the probe's `descendantGeometry` and holds each within one pixel.

## Invariants

1. The window lists every plugin `listPlugins` lists, itself included, with the same enabled state, and writes enablement, a setting and a key that reach `shell.json`, the running instances and the Hyprland layer. Enforced by `scripts/smoke/rows/manager.sh`, which also reads the rows' icon, source, capabilities, binds and errors back.
2. The window is the token width, or the monitor's width less two gutters when that is less, and half the monitor's height, centred on the monitor within one pixel, and it holds the keyboard once open. Enforced by `scripts/smoke/rows/manager.sh`, from the compositor's layer list; the clamp row gives the nested output a 480 by 720 mode, since a headless output stays 0x0 in the sandbox.
3. A click on a row, the title's menu with typed letters and Enter, the back button, Escape, a deep link, the shortcut, the gear and a drag of the page's scroll bar each do what the page says. Enforced by `scripts/smoke/rows/manager.sh` with the nested seat's pointer and keyboard.
4. An edit in progress survives an unrelated configuration change: the same drawn field keeps its focus, text and cursor. Enforced by `scripts/smoke/rows/settings.sh`.

5. `plugin outdated` and `theme outdated` count the commits of a local bare upstream that the checkout lacks. They report zero for a current checkout, and an error row for an unreachable remote, a missing upstream, a directory that is no checkout, a symlink, a missing manifest and a fetch past the timeout. They leave `HEAD`, the work tree and `FETCH_HEAD` unchanged, run no git hook, hand git's transport `GIT_TERMINAL_PROMPT=0`, and keep the lock's descriptor from git. `theme outdated` is refused busy under an exclusive hold of the theme lock and runs under a shared one. Enforced by `scripts/test-vgsh-outdated.sh`. Its controls are copies of `bin/vgsh` that keep hooks, pull instead of fetching, write `FETCH_HEAD`, drop the timeout, the prompt setting or the descriptor close, take no lock or an exclusive one, or list an unreadable directory as empty.
