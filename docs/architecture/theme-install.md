# Theme install

Covers: bin/vgsh-theme-judge

How theme packages are installed, updated and removed under the configuration home. The package format and the runner are [themes.md](themes.md); a catalog install is [theme-catalog.md § Install](theme-catalog.md#install).

## Verbs

`vgsh theme add <git url>`, `vgsh theme update <name>` and `vgsh theme remove <name>` install, fast-forward and delete packages under `${XDG_CONFIG_HOME:-~/.config}/vgs/themes/`. They share the git handling of `vgsh plugin add`, `update` and `remove` ([manager.md](manager.md)): no git hook, no submodule and no package file runs, and no privilege is asked for. They never contact the shell. `bin/vgsh-theme-judge accept` judges a package through `ThemeLogic.acceptPackage`, and `bin/vgsh-theme-judge installed` resolves the directory update and remove act on. `vgsh theme install <name>` installs a catalog package there with no network and no git: [theme-catalog.md § Install](theme-catalog.md#install).

- **Add.** The clone lands in a staging directory beside `themes/`, so no list reads half a package. The package's name is its `theme.json` document name, read by `ThemeLogic.accept`. The judge then accepts the package under that name as an installed one, so the reserved `vgs`, a name `isPackageName` refuses and a bad terminal file are refused. `targets`, `catalog` and `thumbnails` are refused `reserved-name`, since a themes directory's walk skips them (`ThemeLogic.RESERVED_DIRECTORIES`). A source without `theme.json` is refused `absent`. An occupied `themes/<name>` is refused `exists`. An add may shadow a shipped package of its name, as [themes.md § Runner](themes.md#runner) lists it, and its line then names the shipped path: `ok added=<name> path=<dir>[ shadows=<shipped dir>]`.
- **Origin.** `bin/vgsh-theme-judge origin` decides what update and outdated do with an installed package. A package holding `.git` is a git checkout, since a clone always has one and an install never writes one. So a package whose own repository carries the catalog marker stays a git checkout. A package holding the marker and no `.git` is a catalog install, which update and outdated treat as [theme-catalog.md § Install](theme-catalog.md#install) states. Any other directory is taken as a git checkout, which update refuses `not-a-checkout`. Omarchy's `omarchy-theme-extras` (basecamp/omarchy, e332dc9, read 2026-09-28) recognises its git themes by the same `.git` test.
- **Update.** For a git checkout, update refuses a checkout with local changes or untracked files, prints the incoming diff, asks as plugin update does and fast-forwards only: `--yes` gives the answer, a terminal is needed without it, and a no or a missing terminal leaves the checkout at its old commit ([manager.md](manager.md)). A package's files can run code in the applications that load them, and the follow applies them at once, so the question guards the same step it guards for a plugin. The theme lock stays held while update waits for the answer. A version the judge refuses under the installed name, a renamed document included, is rolled back before the refusal. An accepted version then follows as `vgsh theme follow` does for that package alone, still under the lock: when the package is the applied one and the theme file is unedited, update applies it again ([theme-follow.md](theme-follow.md)). The follow's line is update's last and its exit status update's, 3 for a partial re-apply.
- **Remove.** Remove deletes `themes/<name>`, an installed `vgs` and a catalog install included, and never a shipped package, a symlink or a file.
- **Resolution.** Update and remove refuse a name `isPackageName` refuses as `malformed-name`, `targets`, `catalog` and `thumbnails` as `reserved-name`, a name only a shipped package has as `shipped`, and any other absent name as `unknown`.
- **Lock.** Each verb holds the `theme.lock` apply holds, from before it changes `themes/` until it exits, so no apply reads a package mid-change. Add takes it after the clone and the judge. No git call inherits its descriptor, so a gc git detaches never holds it. A held lock exits 75 with `vgsh: refused: theme=<name> reason=busy`, and an apply started meanwhile is refused `reason=busy`.
- **Outdated.** `vgsh theme outdated [--json]` fetches each installed git checkout and reports how far it is behind, holding the theme lock shared; a catalog install's row compares digests instead. It changes no package and runs no hook: [manager.md § Outdated](manager.md#outdated).
- **Refusals.** A judge refusal prints `vgsh: refused: package=<url> reason=<key> ...` on add and `vgsh: refused: theme=<name> reason=<key> ... rolled-back=<commit>` on update. Every other refusal names `theme=<name> reason=<key>`, or the git key the plugin verbs use. Exit 0, 1 on a refusal, 75 when busy, 2 on a bad invocation; the verbs take no `--json`.

## Invariants

1. Add lands a package under its document name from a staging directory and refuses a package the judge refuses, the reserved `vgs`, `targets`, `catalog` and `thumbnails`, a source without `theme.json` and an occupied name, leaving nothing behind; update fast-forwards, refuses a modified checkout, a rewritten history and a diff nobody confirmed, and rolls back a refused or renamed version; remove deletes only an installed directory; none runs a git hook; each is refused busy while the theme lock is held; and no git call inherits the lock's descriptor. Enforced by `scripts/test-vgsh.sh`, with copies of `bin/vgsh` whose install verbs take no lock and whose git calls keep the descriptor as its controls. Update follows the applied, unedited package and leaves a hand edit. Enforced by `scripts/test-vgsh-follow.sh`, with a `bin/vgsh` copy whose update does not follow as its control.
2. A package holding `.git` is a git checkout whatever marker it carries. Enforced by `scripts/test-vgsh-catalog.sh`, with a judge copy that reads the marker first as its control.
