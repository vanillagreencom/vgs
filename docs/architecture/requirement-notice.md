# Requirement notice

Covers: shell/Core/Notices.qml, shell/Hosts/NoticeHost.qml, shell/Core/Registry.qml, shell/Core/Capabilities.qml, shell/Core/HyprlandLayer.qml, scripts/test-notice-logic.js, scripts/smoke/rows/notices.sh, scripts/smoke/rows/notices-control.sh, scripts/smoke/rows/hyprland-consent.sh, scripts/smoke/rows/hyprland-consent-decline.sh, scripts/smoke/fixtures/plugins/acme.needs/**

The core notice host is the centred dialog surface for requirement notices and the Hyprland consent question. It is core, so it works with any set of plugins, the Settings plugin disabled included. `shell/Core/Notices.qml` holds the requirement queue, the install and the one consent slot; `shell/Hosts/NoticeHost.qml` draws one dialog at a time, requirement notice first.

- **Triggers.** Six things raise a requirement notice. `pluginInstalled <id>`, the shell IPC function `vgsh plugin add` calls, starts a rescan, answers as `rescanPlugins` does, and raises the notice once a scan started after the call has ended. `setPluginEnabled`, and the `manager` capability's `setEnabled` through it, raises it when a plugin is turned on. The plugin's own `requirements` capability raises it through `shell.requirements.offer(commands)`. The `manager` capability's `installRequirements(id)`, the Settings window's Install ([settings-window.md](settings-window.md)), raises it for any plugin, and its `act(id, key)` raises it, through `Notices.chosen` as the `doctor` capability does, after a scan, for the commands a status action that installs names while the plugin's value offers it, a user's press no rest refuses ([status.md § Actions and secrets](status.md#actions-and-secrets)). The `requirements` capability's `shell.requirements.missing` reads, and raises nothing: the plugin's declared commands the last scan did not find, in declaration order, bindable, so a plugin shows a command's presence from the scan's probe instead of probing again. `shell.requirements.revision` rises after every ended scan, result or failure, so a plugin can re-read setup state that depends on PATH. The `doctor` capability raises it for another owner through `shell.doctor.offer(owner, commands)`, below.
- **Owners.** A notice belongs to one owner: a plugin, or the core, whose owner id is `core` and whose requirements are `config/requirements.json`, drawn under the name VGS. The scan probes the core's list with the plugins' (`bin/vgsh-scan --core`), and `Registry.requirementOwners` and `Registry.ownerMissing` hold every owner's requirements and missing commands.
- **The doctor capability.** `shell.doctor.offer(owner, commands)` asks, on a user's press, for the notice of the core or of an enabled plugin, for 1 to 16 commands that owner declares. `PluginLogic.noticeOwnerError` refuses `refused: owner=malformed`, `refused: owner=<owner> reason=unknown` and `refused: owner=<id> reason=disabled`, then the offer's own refusals apply, at once. Otherwise it answers `ok`, starts a scan and raises the notice after it, listing each command that scan finds missing: the view that asks read PATH later than the last scan, as after a removal through mise, which rescans nothing. A choice is the user's act, so no rest refuses it. `shell.doctor.missing` is the last scan's missing commands of the core and of every enabled plugin, by owner id, each read a copy; a binding on it follows each scan, enable and disable. The Dev Tools window's VGS section is its consumer.
- **What each asks for.** The install and enable triggers list every missing command and keep the notice open while a command the plugin does not mark optional is missing. A plugin missing only optional commands raises none. A request from the manager lists and keeps open every missing command, optional or not, since the user asked to install them; a plugin missing nothing answers `refused: requirements=<id> reason=satisfied`. An offer lists and keeps open each of its commands still missing, optional or not. It names 1 to 16 commands, each declared in the plugin's own manifest, so a plugin never offers a package it did not declare. It answers `ok`, `satisfied` when none is missing, `refused: requirements=malformed` for anything but a list of 1 to 16 strings, or `refused: requirement=<command> reason=undeclared`.
- **Queue.** One notice per owner: a trigger for an owner that holds one merges its commands into it and answers `ok`. At most 8 plugins hold a notice. The first shows and the rest wait, and a ninth answers `refused: notices=full limit=8`. Not now, Escape and Close drop the shown notice and rest the plugin's own offers for 10 minutes: an offer then answers `refused: requirements=<id> reason=resting retry-ms=<ms>`. The install and enable triggers are the user's own acts, so no rest refuses them. The ceilings are core policy, like the toast stack's.
- **Surface.** One `OverlaySurface` in namespace `vgs:notice` ([layers.md](layers.md)), on the monitor that was focused when the notice came to the front, taking the keyboard on demand. It fills the area other layers leave free, less `dialog.margin` on every edge, and the dialog sits in its centre. Only the dialog takes pointer input, so the bar and the layers below keep their clicks. Omarchy's notification popups (basecamp/omarchy `8b4eae6`, `shell/plugins/notifications/Service.qml`) use one full-screen overlay window with a mask on the popups too, but ignore reserved space and compute the bar's clearance themselves. VGS lets the compositor subtract reserved space instead, which holds for any layer that reserves space, on any edge. It exists only while a notice shows and its install does not run, so the floating TUI the install opens on the same monitor shows whole; a notice the install leaves open maps again as a new window that takes the keyboard. The `Dialog` component draws it ([components.md](components.md)).
- **Hyprland consent.** `HyprlandLayer.qml` owns the consent question. The notice host draws it only when no requirement notice shows. It offers Connect and Not now, and its command disclosure holds `vgsh hypr wire`. Connect answers the owner to run the wire and reload sequence. Not now, Escape and Close answer decline. [hyprland-wiring.md § The line](hyprland-wiring.md#the-line) gives the state machine and marker.
- **Managers.** `bin/vgsh-pkg detect --json` runs when the first notice arrives and again after each install. The notice waits for the first answer. A detection that fails is logged as `notices: detect=failed exit=<code> status=<status> <first stderr line>`, and the notice lists the commands without packages.
- **Rows.** Each listed requirement reads as its purpose, with a hint under it naming the command, this system's package for it and whether it is optional. No row draws a command to run: the command Install runs, `PluginLogic.noticeView`'s `commandLine`, sits only behind the dialog's `CommandDisclosure`, closed until asked, whose toggle and Copy the dialog's Tab cycle reaches, and a notice with no Install has none ([D061](../decisions/D061-no-manual-commands.md), [status.md § Setup steps](status.md#setup-steps)). `scripts/check-user-commands.py`'s `drawn-command-line` fails any drawn property bound to a `commandLine`.
- **Install.** The notice offers Install and Not now when a detected manager installs a listed package, and Close alone otherwise. Its message then names each nix package to add to the system configuration, or says the commands are installed by hand. Install opens the core TUI `core/requirements-install`, `vgsh pkg run install [--manager <id>] <package>...`, for the first group `PackageManagers.installGroups` makes: one manager per press, primary first. The notice stays at the front of the queue until one scan after the TUI's run ended, even when a scan the run's own steps asked for already finds its commands, so no waiting notice comes forward while the terminal still holds the install's key: `PluginLogic.noticeSettle` keeps it. A notice whose required commands that scan finds is closed; otherwise it stays, offers the next group, and names a run that did not end with code 0. The package manager asks for root in the terminal, never in the shell ([tui.md](tui.md)).

Omarchy (basecamp/omarchy `e332dc97`) installs a missing terminal from `omarchy-default-terminal`, which runs itself again with `--install` in its floating terminal through `omarchy-launch-floating-terminal-with-presentation`. VGS does the same for every declared requirement: the question is a shell dialog, and the install is a floating TUI that runs `vgsh pkg run`.

## Invariants

1. A notice lists only commands its owner declares, raises none for optional commands alone, merges per owner, asks for a `doctor` request's owner only when it is the core or an enabled plugin, rests a plugin's offers after Not now and never the user's triggers, holds at most 8 plugins, keeps the installing notice through a scan until its run's own, and installs through a manager that installs. Enforced by `scripts/test-notice-logic.js`, with a judge copy per rule as control.
2. `vgsh plugin add` and enabling a plugin each raise the notice in a running shell, with the Settings plugin disabled; it maps on the focused monitor with the keyboard, draws each requirement as its purpose and the install command only behind a closed Show command, its surface clears the bar by `dialog.margin` with the dialog in its centre, a click on a bar widget and one beside the dialog pass through while one on the dialog's title does not, Escape closes it, Install hands the terminal `vgsh pkg run install` with the primary's package, the notice has no surface while the run is live, a scan during the run keeps the installing notice in front of a waiting one, and only the scan after the run closes it. Enforced by `scripts/smoke/rows/notices.sh` in the nested sandbox, with the fixture `acme.needs`, a stand-in `bin/vgsh-pkg` for detection and `scripts/smoke/rows/tui.sh`'s stand-in terminal. The rescan row's control is the install before the command exists, which leaves the notice open. The same row reads `shell.requirements.missing` from the fixture before the install, after it and after the command goes; the reading before the install and the one after it are each other's control. `scripts/test-notice-logic.js` fails on a judge copy whose `noticeSettle` drops the installing notice. The enable trigger's control is `scripts/smoke/rows/notices-control.sh`, the suite's last row: it stops the running shell, starts a copy of the tree whose `Plugins.setEnabled` does not call `Notices.enabled` as the guarded shell, and reads no notice after enabling `acme.needs`.
3. The `doctor` capability raises an enabled plugin's notice from another plugin's press after a scan, raises none for a core command that scan finds, refuses a command the core does not declare and a disabled or unknown owner, and its `missing` follows the scan. Enforced by `scripts/smoke/rows/devtools.sh` in the nested sandbox, whose control copy of the Dev Tools service ignores a change of `missing` and keeps a disabled plugin's requirement, and the owner rule by `scripts/test-notice-logic.js`.
