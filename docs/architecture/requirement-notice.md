# Requirement notice

Covers: shell/Core/Notices.qml, shell/Hosts/NoticeHost.qml, scripts/test-notice-logic.js, scripts/smoke/rows/notices.sh, scripts/smoke/fixtures/plugins/acme.needs/**

The requirement notice is the core's centred dialog that lists a plugin's missing commands and installs their packages with one press. It is core, so it works with any set of plugins, the Settings plugin disabled included. `shell/Core/Notices.qml` holds the queue and the install, `shell/Hosts/NoticeHost.qml` draws it, and `PluginLogic.js` makes every decision: `noticeRequest`, `noticeAdmit`, `noticeView` and `noticeDetected`.

- **Triggers.** Three things raise a notice for a plugin. `pluginInstalled <id>`, the shell IPC function `vgsh plugin add` calls, starts a rescan, answers as `rescanPlugins` does, and raises the notice once a scan started after the call has ended. `setPluginEnabled`, and the `manager` capability's `setEnabled` through it, raises it when a plugin is turned on. The plugin's own `requirements` capability raises it through `shell.requirements.offer(commands)`.
- **What each asks for.** The install and enable triggers list every missing command and keep the notice open while a command the plugin does not mark optional is missing. A plugin missing only optional commands raises none. An offer lists and keeps open each of its commands still missing, optional or not. It names 1 to 16 commands, each declared in the plugin's own manifest, so a plugin never offers a package it did not declare. It answers `ok`, `satisfied` when none is missing, `refused: requirements=malformed` for anything but a list of 1 to 16 strings, or `refused: requirement=<command> reason=undeclared`.
- **Queue.** One notice per plugin: a trigger for a plugin that holds one merges its commands into it and answers `ok`. At most 8 plugins hold a notice. The first shows and the rest wait, and a ninth answers `refused: notices=full limit=8`. Not now, Escape and Close drop the shown notice and rest the plugin's own offers for 10 minutes: an offer then answers `refused: requirements=<id> reason=resting retry-ms=<ms>`. The install and enable triggers are the user's own acts, so no rest refuses them. The ceilings are core policy, like the toast stack's.
- **Surface.** One layer window in namespace `vgs:notice`, on the overlay layer, centred on the monitor that was focused when the notice came to the front, taking the keyboard on demand. It exists only while a notice shows. The `Dialog` component draws it ([components.md](components.md)). Each row is a missing command as the command line names it, `<command>[ (<package>)][ optional]: <purpose>`.
- **Managers.** `bin/vgsh-pkg detect --json` runs when the first notice arrives and again after each install. The notice waits for the first answer. A detection that fails is logged as `notices: detect=failed exit=<code> status=<status> <first stderr line>`, and the notice lists the commands without packages.
- **Install.** The notice offers Install and Not now when a detected manager installs a listed package, and Close alone otherwise. Its message then names each nix package to add to the system configuration, or says the commands are installed by hand. Install opens the core TUI `core/requirements-install`, `vgsh pkg run install [--manager <id>] <package>...`, for the first group `PackageManagers.installGroups` makes: one manager per press, primary first. The dialog is busy until one scan after the TUI's run ended. A notice whose required commands that scan finds is closed; otherwise it stays, offers the next group, and names a run that did not end with code 0. The package manager asks for root in the terminal, never in the shell ([tui.md](tui.md)).

Omarchy (basecamp/omarchy `e332dc97`) installs a missing terminal from `omarchy-default-terminal`, which runs itself again with `--install` in its floating terminal through `omarchy-launch-floating-terminal-with-presentation`. VGS does the same for every declared requirement: the question is a shell dialog, and the install is a floating TUI that runs `vgsh pkg run`.

## Invariants

1. A notice lists only commands the plugin declares, raises none for optional commands alone, merges per plugin, rests a plugin's offers after Not now and never the user's triggers, holds at most 8 plugins, and installs through a manager that installs. Enforced by `scripts/test-notice-logic.js`, with a judge copy per rule as control.
2. `vgsh plugin add` and enabling a plugin each raise the notice in a running shell, with the Settings plugin disabled; it maps centred on the focused monitor with the keyboard, Escape closes it, Install hands the terminal `vgsh pkg run install` with the primary's package, and only a rescan that finds the required command closes it. Enforced by `scripts/smoke/rows/notices.sh` in the nested sandbox, with the fixture `acme.needs`, a stand-in `bin/vgsh-pkg` for detection and `scripts/smoke/rows/tui.sh`'s stand-in terminal. The rescan row's control is the install before the command exists, which leaves the notice open. No committed control removes the enable trigger: the shell cannot be restarted on a copy inside the sandbox run.
