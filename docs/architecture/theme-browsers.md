## Chromium

Chromium, Google Chrome, Microsoft Edge and Brave read one colour input from outside the browser, the managed policy `BrowserThemeColor`. `bin/vgsh-browser-policy` writes it: [D029](../decisions/D029-chromium-policy-writer.md). Its `--help` header states its two commands, its halves and its exit statuses.

- **Setup.** `vgsh theme browser-policy install`, run once by the owner in a terminal, installs the sudoers rule `/etc/sudoers.d/vgs-browser-policy`, checked by `visudo -c` first, then the writer at `/usr/local/bin/vgs-browser-policy`, both `root:root`. The rule names the installing user, the writer's path and six `[0-9a-f]` classes as its only argument. Until the writer is on `PATH` the target is skipped with `setup-absent`: [theme-targets.md § Targets](theme-targets.md#targets). Removing both files with `sudo rm` undoes the setup.
- **Colour.** `chromium.color` holds `color.background` as six lowercase hex digits. The hook runs on every apply, `reload.always`, since a browser installed or a policy changed since the last apply takes the write without a theme change.
- **User half.** The writer resolves every command in the system directories alone. When every policy directory that exists, or whose browser is installed, holds the canonical `color.json`, a regular file `root:root 0644` with the policy's bytes, it exits 0 and runs nothing. Otherwise it runs `sudo -n /usr/local/bin/vgs-browser-policy <rrggbb>`, which never prompts, then runs `<browser> --refresh-platform-policy --no-startup-window` for each installed browser whose process runs as the user. A refused `sudo` fails the hook, and the target stays `reload-pending`. A refresh's status is not checked: the browser reads the policy at its next start.
- **Root half.** For each of `/etc/chromium/policies/managed`, `/etc/opt/chrome/policies/managed`, `/etc/opt/edge/policies/managed` and `/etc/brave/policies/managed` that exists, or whose browser is installed, it requires `/etc`, and `/etc/opt` for the second two, to be real directories root owns and only root writes. It then makes each entry below them a real directory `root:root 0755`, top-down, creating a missing one, and refuses a link or a file on the way. It replaces a link or directory at `color.json`, then renames a staged file over it. A refused directory fails the run and the others are still written.
- **Policy.** `{"BrowserThemeColor": "#rrggbb", "BrowserColorScheme": "device"}`: the browser seeds its colours from `BrowserThemeColor`, and `BrowserColorScheme` `device` makes its light or dark mode follow the desktop's. The policy is machine-wide, so the browser shows itself as managed by an organisation, for every user of the machine.

## Zen

Zen draws its toolbars, panels, URL bar and container colours from the theme: the containers from the terminal slots, the rest from the `color` tokens. The user sets `toolkit.legacyUserProfileCustomizations.stylesheets` to `true` once in `about:config`, since Zen reads `userChrome.css` only with it, and only at startup: a theme applies on the next restart. Apply never edits `prefs.js` or `user.js`.

## Pywalfox

pywalfox's native host reads pywal's `colors.json` from `${XDG_CACHE_HOME:-~/.cache}/wal/`: its `colors`, at least sixteen in key order, and a `wallpaper` key it requires, empty here. `pywalfox update` has the connected browser fetch the file again and exits 0 when no browser is connected. A `colors.json` pywal itself wrote is the user's, and the target is skipped with `entry-occupied`. Source: pywalfox-native `config.py`, `fetcher.py` and `__main__.py`.

## Invariants

1. The `zen` target writes its colours as `#rrggbb`, its container colours from the terminal slots, and keeps its import first in each profile of `~/.zen`, else `~/.config/zen`, creating the file and keeping its own text; it never runs `zen-browser`. The `pywalfox` target writes pywal's `colors.json` shape with a wallpaper and sixteen slots, links it as `colors.json` under `XDG_CACHE_HOME` alone, and runs `pywalfox update` on changed bytes, a failure leaving it `reload-pending` until `vgsh theme reload`. Enforced by `scripts/test-vgsh-browsers.sh` under a PATH holding stub `zen-browser` and `pywalfox`, with `target.json` copies that write `hex8`, try `~/.config/zen` first, link under HOME and drop the hook as its controls.
2. The `chromium` target writes `color.background` as six hex digits, is skipped with `setup-absent` until `vgs-browser-policy` is on `PATH`, in apply and in reload, runs its hook with that colour on every apply that lands it, unchanged bytes included, never runs a browser, and stays `reload-pending` when the hook fails. `vgsh theme browser-policy install` runs the writer's `install` alone. Enforced by `scripts/test-vgsh-browsers.sh` under a PATH holding stub `chromium` and `vgs-browser-policy`, with a `target.json` copy that drops `always` and judge copies that ignore the setup in apply and in reload as its controls.
3. The writer takes six lowercase hex digits and nothing else in either half; skips a canonical policy with no `sudo`; elevates through `sudo -n` of its installed path alone; refreshes only installed browsers that run; writes only directories that exist or whose browser is installed; refuses a chain through a link or an untrusted system directory while writing the others; hardens a writable entry to 0755; replaces a planted link without following it and a planted directory; and installs a rule `visudo` accepted, naming the user and six hex classes, before the writer, stopping at the first failure. Enforced by `scripts/test-vgsh-browser-policy.sh`, which runs a copy under a temporary prefix with a stub `sudo` running the root half under `unshare -r`, with copies that widen the argument, ignore the owner, follow a link, ignore a mode, skip the chmod, skip the replacement, create every directory and refresh every browser as its controls.
