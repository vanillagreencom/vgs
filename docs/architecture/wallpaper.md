# Wallpaper pipeline

Covers: quickshell/vshell/Common/SessionData.qml, quickshell/vshell/Services/VGSThemeService.qml, quickshell/vshell/Services/WallpaperCyclingService.qml, quickshell/vshell/Modules/WallpaperBackground.qml, bin/vshell_wallpaper_thumbs.py

Which value each actor owns, in what order applies reach the helper, and what an interrupted thumbnail sweep leaves behind. Palette derivation and app targets are in [theme.md](theme.md); wallpaper downloads are in [theme-catalog.md](theme-catalog.md).

## Entry points

| Entry point | Calls | Writes |
|---|---|---|
| Wallpaper switcher, Dash Wallpapers, Settings Themes | `VGSThemeService.setWallpaper` → `vshell theme set-wallpaper` | shell: `SessionData`. Helper: package data, and the targets [theme.md](theme.md) names — a pick that keeps the palette moves only the targets whose template names the wallpaper role, which [theme.md](theme.md) names, while `--extract` re-derives every role and moves every enabled target |
| Theme switcher, Dash Themes, Settings Themes, Icons tab, catalog download | `VGSThemeService.applyBlueprint` → `vshell theme apply` | shell: `SessionData`. Helper: every enabled target |
| Switcher "This monitor", Dash per-monitor buttons, Settings toggle, `wallpaper` IPC | `SessionData.setWallpaper`, `setMonitorWallpaper` and `setPerMonitorWallpaper` | shell only: `session.json` |
| `vshell theme apply` from a terminal | the helper directly | helper only; the shell adopts it through `MethodTheme`'s `theme.json` watcher |
| `WallpaperCyclingService` | `SessionData.setWallpaper` and `setMonitorWallpaper` | shell only: `session.json` |
| Thumbnail sweep | `vshell theme wallpaper-thumbs --all` | the thumbnail cache only |

## Invariants

- The wallpaper on screen and the palette's input wallpaper are separate values with one writer each, and neither is read as the other. `SessionData` alone writes the desktop's `session.json` under the state directory, which holds `wallpaperPath`, the per-mode and per-monitor maps and the fill modes, and `Modules/WallpaperBackground.qml` renders from `SessionData.getMonitorWallpaper` alone. The greeter profile cache holds a second file of that name, a snapshot `sync_profile_cache` in `bin/vshell_helper.py` writes and `SessionData`'s `greeterSessionFile` reads with `blockWrites`, so the greeter reads it and never writes it. The helper alone writes `theme-current.json` and a package's `theme.json`, which record the image the applied palette was derived from, the first as a rooted reference and the second as a bare file name inside the package's own `backgrounds/`; `~/.config/vshell/theme.json` is the `vgs-shell` target's render of that value rather than a second record of it. The two differ by design where `wallpaperSource` is `folder`, and under per-monitor or per-mode assignment. `MethodTheme`'s `theme.json` watcher is how the shell hears a `vshell theme apply` run from a terminal, which writes no session state.
- An apply issued through `VGSThemeService._runApply` reaches the helper only while no other such apply is running, so those applies run in request order. Nothing else does: every other mutating `theme` subcommand the service launches takes the lock without the slot, and `MethodTheme._runThemeHelper` issues mutating subcommands of its own outside the service entirely. `theme_mutation_lock` in `bin/vshell_helper.py` stops two helper processes interleaving their writes but does not order them, so `VGSThemeService._runApply` queues an apply while another is running and `_finishApply` starts the oldest waiting one before it emits its signals. Without that, two picks in quick succession race for the lock, the older one can write `theme.json` last, and the desktop shows one image while the palette on screen was derived from another. `scripts/test-theme-apply-queue.js` checks the ordering and the drain order.
- A refused apply leaves the desktop on the last apply that succeeded. `session.json` is written only by a success, and every success commits its own wallpaper, so what it holds is the last apply that landed. The wallpaper slot in `VGSThemeService` governs the optimistic `selectedWallpaper` highlight alone, not that write: the highlight is written when an apply starts and rolled back on refusal, but only while that request is still the newest pick, so a refusal cannot take it off a later pick queued behind it. `scripts/test-theme-apply-queue.js` executes a success with a pick already queued behind it.
- Enabling per-monitor wallpaper mode preserves each screen's current image and disables retained cycling. A per-monitor assign is a synchronous `SessionData` write with no helper call, so it has no window a monitor can vanish in: the screen is checked, written and read back in one frame, a screen that is already gone is refused by name, and one that disconnects later keeps its map entry and shows it again on return. `scripts/test-switcher-scope.js` checks the transition.
- Removing a wallpaper from a theme and deleting it are separate verbs. `theme wallpaper-remove` hides the file by name and deletes nothing, and `theme wallpapers --all` still lists it, marked `removed`. `theme wallpaper-delete`, run by `VGSThemeService.wallpaperDelete`, deletes an image only directly inside the wallpaper folder or a user theme's `backgrounds/`, and refuses every path it receives as `--applied`. The service passes each image path `SessionData.referencedWallpapers` returns, which covers the shown and per-mode paths and every per-monitor entry, a disconnected monitor's included, and `SettingsData.lockScreenWallpaperPath`. `test_theme_wallpaper_delete_removes_the_file_and_its_set_names` in `scripts/check-vshell-helper.py` checks each refusal and the deletion.
- `theme-current.json`, `~/.config/vshell/theme.json` and `session.json` record a wallpaper as a reference rooted on `${VSHELL_ROOT}`, never as a path into the directory the applying shell ran from. A shell started from a checkout or a worktree reads its built-in theme packages out of that directory, so an absolute path to one pins it and every monitor loses its wallpaper once the directory goes. Recording is one containment test, `portable_ref` in `bin/vshell_helper.py`: a path inside the running root becomes a rooted reference and every other path is recorded as it stands, so a picked wallpaper this installation does not own is never rewritten. `theme-current.json` takes the reference from `applied_theme_state` and `~/.config/vshell/theme.json` from the `{wallpaper.ref}` token, which is the shell target's alone, since every other target writes a config that resolves no VGS token. `Common/Paths.qml` mirrors recording and resolving for `session.json`, which the shell writes on a coalesced timer no subprocess can sit inside, and `Common/settings/SessionStore.js` applies the mirror to each key `SessionSpec.js` marks `ref` or `refMap`, through the one wrapper pair in `SessionData`. `settings.json` holds wallpaper paths too, in `wallpaperFolder`, `greeterWallpaperPath` and `lockScreenWallpaperPath`, and no rule here covers them. `scripts/lib/wallpaper-ref-cases.json` is the one case table `scripts/test-wallpaper-refs.py` and `scripts/test-wallpaper-refs.js` both run.
- Repairing a background another installation recorded emits a path only when the file it names is present on this installation. `recovered_package_ref` in `bin/vshell_helper.py` is the one owner: a path inside `~/.config/vshell/themes` answers as it stands, since the copy it names is the one the user chose, and every other absolute path whose tail is `themes/<package>/backgrounds/<file>` is looked for under the running root and then under the user's packages, answering with the first that holds it. A path naming no package here comes back untouched. Without the filesystem test the rule is a guess about what a path means, and a reader whose root holds no packages rewrites every background into a file that is not there. `Common/Paths.qml` carries no repair rule, because the shell cannot run that test synchronously.
- The repair reaches state two ways, because a reader that opens a file sees its bytes rather than what a helper call returns. `repair_theme_state`, which `theme init` runs on every shell start, rewrites `~/.config/vshell/theme.json` and `theme-current.json` in place when their recorded wallpaper is one this installation can repair. `session.json` is repaired per key: `SessionData._repairWallpapers` hands every absolute path the store holds to `theme wallpaper-repair`, which answers from the same owner, and `SessionStore.mapRefs` writes the answers back in place, so each monitor and each mode keeps its own value. These two must not meet. `MethodTheme`'s watcher re-reads `theme.json` for the repair's rewrite exactly as it does for a terminal apply, and its sync calls `SessionData.setWallpaper`, which writes that one image to every connected monitor and to the active mode; letting a repair through it replaces the per-monitor and per-mode values the per-key repair restores, and session.json then no longer names the files any later repair would ask about. `theme init --json` answers with the `repaired` list naming the files it rewrote, and `VGSThemeService` carries that to `Theme.themeInitStarted` and `Theme.themeInitFinished`: the sync is held from the launch until the answer, and released on the verdict of `VGSThemeService._themeInitOutcome`, which owns what the answer means. What it turns on is whether the answer names a rewrite of `theme.json`, the one change the watcher cannot tell from an apply; an answer it cannot read holds the sync too. The `recover` rows in `scripts/lib/wallpaper-ref-cases.json` name the package files each reading installation holds, and `scripts/test-wallpaper-refs.js` drives both routes against one store.
- The greeter's copy of `theme.json` and `session.json` carries resolved paths, not references. `sync_greeter_runtime` stages `quickshell/vshell` and the runtime bin files into the cache and no `themes/`, while `bin/vshell` sets `VSHELL_ROOT` to that staged runtime, so a rooted reference there names nothing and the login screen shows no wallpaper. `current_theme_json` and `current_session_json` in `bin/vshell_helper.py` resolve on the way in, over the keys `SESSION_WALLPAPER_KEYS` names and `SessionSpec.js` owns.
- A wallpaper thumbnail is built into a temp file named for the building process, and a sweep reclaims a temp file whose process is gone. `temp_path` and `reclaimable` in `bin/vshell_wallpaper_thumbs.py` own both halves, and `_prune_to` is the one sweep both `prune_orphans` and `build_all` run, each handing it the keys of the complete wallpaper set. A pid the kernel has reissued reads as live and the file waits for the next sweep, so a build still decoding never loses its temp file. `scripts/test-wallpaper-thumbs.py` checks the keep and the reclaim.
- `VGSThemeService._sweepWallpaperThumbs` dispatches a thumbnail sweep when a wallpaper read finds a current-theme identity missing and under the attempt cap, when a flow the shell ran asked for one through `requestThumbnailSweep`, or when the session's discovery sweep is still pending. The discovery sweep is dispatched at startup once theme init answers, is spent by the first sweep that dispatches, and is never armed again, so a theme installed or removed outside the shell before startup is built or pruned without a watcher on the themes directory; one changed outside the shell later waits for the next sweep. An unparseable helper answer restores a requested sweep and never the discovery sweep. `scripts/test-thumb-sweep.js` checks the plan and that the discovery sweep is spent at dispatch and never armed again, and `scripts/test-theme-startup.js` that startup dispatches it.
