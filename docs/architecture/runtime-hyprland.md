# Runtime: Hyprland

Covers: shell/Core/Compositor.qml, shell/Core/Dispatch.js, scripts/test-dispatch.js, shell/Core/HyprlandLayer.qml, shell/Core/HyprlandLayer.js, scripts/smoke/rows/hyprland.sh, scripts/smoke/rows/overlay-capture.sh, scripts/smoke/rows/windows.sh, scripts/smoke/rows/compositor-reveal.sh, scripts/smoke/rows/compositor-dispatchers.sh

The Hyprland facts the shell, its Hyprland layer and the smoke rows rest on, each with the source or the reading that establishes it, and the rules every dispatch follows. [runtime.md](runtime.md) holds the process, the runner and the measurement tools.

- What a Lua configuration shows through `hyprctl` in v0.56.2, from its source (`src/debug/HyprCtl.cpp`, `src/config/lua/bindings/`) and read in `scripts/smoke/rows/hyprland.sh`: `binds -j` gives a Lua bind the dispatcher `__lua` and a registry index as `arg`, so only its `description` names what it runs. No command reads a layer rule back, and a rule's Lua handle answers only `is_enabled`. `configerrors -j` lists what a binding function refuses, such as an unknown field, an out-of-range value or a key string it cannot parse, with its file and line, even from a file run through `pcall`; the function returns and the file goes on. A Lua runtime error, such as a call to a missing function, stops that file inside `pcall` and reaches no list. `getoption -j` takes `general:col.active_border` or `general.col.active_border` and prints a border as `gradient`, each colour hex `aarrggbb` without leading zeros, then the angle in `deg`. A bind resolves a keycode through the compositor's configured layout unless `input:resolve_binds_by_sym` is set when the keyboard appears (`CKeybindManager::onKeyEvent`). `wtype` assigns its own keycodes, so a key it types reaches a bind only with that setting on. A virtual keyboard's key runs binds unless the input method owns that keyboard.
- A `hl.window_rule` with a `name` already registered changes that rule, so `enabled = false` after the line disables it (`src/config/lua/bindings/LuaBindingsConfigRules.cpp`, v0.56.2). A new floating window that asks no position, as no xdg toplevel can, is centred with or without `center` on the monitor's logical box less its reserved space and `general:float_gaps` (`src/layout/algorithm/floating/default/DefaultFloatingAlgorithm.cpp`, `src/layout/space/Space.cpp`). Read in `scripts/smoke/rows/hyprland.sh` on 2026-09-28: under a 26 px bar, an 875 × 600 window's top sat at 180, not at 166.5, the whole monitor's centre.
- A floating xdg toplevel that no rule gives a size keeps the size its first buffer has: the Settings window asked 600 × 466 on a 1755 × 933 nested monitor and mapped at 600 × 466, read in `scripts/smoke/rows/windows.sh` on host cachy on 2026-09-29. A new window takes the focus, and a floating one stacks over the windows before it: the toplevel helper, a floating TUI's stand-in terminal and the Settings window each read back as `activewindow` once mapped, and the stand-in terminal's colour is the pixel at the centre of the Settings window under it (`scripts/smoke/rows/manager.sh`). The border is drawn outside the window's box, `general:border_size` pixels wide: at size 4, the four pixels left of the box read the border colour and the fifth does not, through `grim` on the nested output. A layer surface that takes the keyboard on demand still takes it when it maps over a focused window: the requirement notice does over the Settings window.
- The Lua window dispatchers take a `window = "address:0x…"` selector: `hl.dsp.window.move({ x, y, relative = true, window })` moves a floating window, `hl.dsp.window.float({ action = "toggle", window })` tiles or floats it, `hl.dsp.focus({ window })` focuses it and `hl.dsp.window.close({ window })` closes it, each answering `ok` and read back from `clients -j` and `activewindow -j` in `scripts/smoke/rows/windows.sh` (`src/config/lua/bindings/LuaBindingsDispatchers.cpp`, v0.56.2). A selector no client matches moves nothing: a move aimed at the title of a layer surface leaves the layer where it was.
- Moving the pointer into another monitor focuses that monitor while `misc:mouse_move_focuses_monitor` is on, its default (`src/config/values/ConfigValues.cpp`, v0.56.2), so a click on a bar focuses that bar's monitor, where Hyprland maps the next window.
- `hyprctl reload config-only` runs `hyprland.lua` again, a file it loads with `dofile` included, and skips reconfiguring the monitors (`hyprctl --help`); it answers `ok`. The Hyprland layer reloads this way after each write, and `scripts/smoke/rows/hyprland.sh` reads the binds and the active border back after it. The reload still drops a monitor rule `hyprctl eval` added and applies a rule a loaded file names for an output, but it does not give an output the default rule's mode. Read in a nested Hyprland 0.56.2 on host cachy on 2026-09-29, `WAYLAND-1` on a 1755 × 933 window, twice each: held at 3510 × 1866 and scale 2 through `hyprctl eval`, then dropped to scale 1 the same way, the output stays at 3510 × 1866 and scale 1 after the reload; with a file `dofile` loads naming 3510 × 1866 at scale 2, the same drop and reload give it 3510 × 1866 at scale 2 again; with no such file, an output at 3510 × 1866 and scale 2 from `hyprctl eval` keeps that mode and scale through `reload config-only` and a full `hyprctl reload`, and the default `output = ""` rule at scale 1 is not applied to it. The smoke harness therefore keeps a held rule in a file its `hyprland.lua` runs, and `scripts/smoke/rows/hidpi.sh` reads a reload bring it back and, without the file, not.
- On Hyprland v0.56.2, `CConfigManager::reload()` in `src/config/lua/ConfigManager.cpp` resets every `m_configValues` entry and the animation tree before it reruns `hyprland.lua`; `src/config/lua/types/LuaConfigInt.cpp` sets an int option back to its default in `CLuaConfigInt::reset()`. Read back in `scripts/smoke/rows/hyprland.sh` on 2026-09-29: after a layer set `general:border_size` to 4 and `decoration:rounding` to 8, turning off those layer groups removed their lines and `hyprctl getoption` returned 1 and 0.
- Bringing a window into view, `Compositor.reveal`, rests on `hl.dsp.focus({ window })` (`Actions::focus` in `src/config/shared/actions/ConfigActions.cpp` and `CFocusState::rawWindowFocus` in `src/desktop/state/FocusState.cpp`, v0.56.2). It switches to the window's workspace, on the window's monitor; it shows a hidden special workspace on the focused monitor through `setSpecialWorkspace`, never a toggle, so it never hides one already shown; it makes a background group tab current (`CLayoutManager::bringTargetToTop`); and under a fullscreen window it follows `misc:on_focus_under_fullscreen`, whose default 2 ends the fullscreen. `scripts/smoke/rows/compositor-reveal.sh` reads each case back; [D051](../decisions/D051-notification-actions-reveal-the-sender.md) records why the shell reveals. In the nested sandbox a headless output lists no size, so the pointer cannot follow the focus there and Hyprland hands the monitor focus back to the pointer's monitor; the window stays focused on its monitor's shown workspace (read on 2026-09-29).
- `clients -j` gives `focusHistoryID` 0 to the window focused last and higher numbers to older focus. It is history, not focus: the window keeps 0 after the focus moves to an empty workspace, where `activewindow -j` answers `{}`, so `Compositor.reveal` takes the focused window from `activewindow` and ranks by `focusHistoryID` alone (read in `scripts/smoke/rows/compositor-reveal.sh`). `hyprctl --batch "j/clients;j/activewindow;j/monitors"` answers the three in one pass of the compositor, joined by `\n\n\n` (`dispatchBatch` in `src/debug/HyprCtl.cpp`, v0.56.2), so they describe one moment. `clients -j` gives `visible: false` to a background group tab, whose `hidden` stays false. The event socket reports `activewindowv2>>ADDR` on each focus and `workspacev2` on each switch, ADDR the address in hexadecimal without `0x`. An application's `xdg_activation_v1.activate` with a token Hyprland issued calls `CWindow::activate` (`src/protocols/XDGActivation.cpp`, `src/desktop/view/Window.cpp`): it posts `urgent>>ADDR` and focuses the window only under `misc:focus_on_activate`, default false.
- A headless output in the nested session gets no mode on an NVIDIA host. `hyprctl output create headless NAME` lists the monitor at 0x0 and scale 1, with or without a monitor rule for NAME. The nested compositor runs Aquamarine's Wayland backend and no DRM backend, so `CHeadlessBackend::getRenderFormats()` in `src/backend/Headless.cpp` (aquamarine v0.15.1) returns a fixed list whose 8-bit formats carry the modifier `DRM_FORMAT_INVALID`. That value is 0, the value of `DRM_FORMAT_MOD_LINEAR`, so `CGBMBuffer::CGBMBuffer` in `src/allocator/GBM.cpp` asks for a linear buffer, then for `GBM_BO_USE_LINEAR`, and NVIDIA refuses both, as the file's own comment says. Hyprland's log then holds, for each mode it tries, `Couldn't allocate a gbm buffer with size [1280, 720] and format XR24` and `REJECTED available mode 1280x720@60.00Hz!`, then `has NO FALLBACK MODES, and an INVALID one was requested: 0x0@60.00Hz`. The nested Wayland output allocates with NVIDIA's tiled modifier and works. Read in a nested Hyprland on host cachy (NVIDIA GPU, Hyprland 0.56.2, aquamarine 0.15.1) on 2026-09-29.
- The nested Wayland output takes any mode and an integer scale through `hl.monitor` in `hyprctl eval`. On a 1755 × 933 nested window, `mode = "3510x1866", scale = 2` read back from `hyprctl -j monitors` as 3510 × 1866 at scale 2, and `grim` on the nested socket captured a 3510 × 1866 PNG, in device pixels; `mode = "1755x933", scale = 1` read back as before. Double the mode at scale 2 keeps the logical size. Read on host cachy on 2026-09-29. `scripts/smoke/rows/hidpi.sh` and `scripts/sandbox-shots.sh --scale 2` hold this mode before they start a shell, since a running shell does not follow a scale change ([runtime-qml.md](runtime-qml.md)).
- Hyprland runs global binds before a layer surface receives a focused key. The overlay capture uses a submap because a Quickshell layer with keyboard focus alone cannot stop a default-map bind behind it. Read in `scripts/smoke/rows/overlay-capture.sh` on host cachy on 2026-09-29: a harness `SUPER+K` bind wrote no marker while `vgs:overlay` was mapped.
- In Hyprland v0.56.2, `hl.bind` made inside a submap belongs to that submap, and an active submap blocks default-map binds while unbound keys still go to the focused surface. `hl.dsp.submap("reset")` returns to the default map. Read in `scripts/smoke/rows/overlay-capture.sh` on host cachy on 2026-09-29: the same `SUPER+K` bind fired after Escape closed the browser.
- A mapped overlay under the capture submap keeps unbound text off a later mapped xdg toplevel. Read in `scripts/smoke/rows/overlay-capture.sh` on host cachy on 2026-09-29: a helper toplevel mapped behind the theme browser logged no `key` line after `z`, and a copy of `SummonHost.qml` that used `WlrKeyboardFocus.OnDemand` for the overlay also logged no helper key while `vgs:capture` was active.
- `layer.closed` fires when the overlay client goes away. In the event, the closing layer can still be in the layer list, so the capture layer passes that event object into its `hl.get_layers()` scan and ignores it while it checks for other mapped `vgs:overlay` layers. Read in `scripts/smoke/rows/overlay-capture.sh` on host cachy on 2026-09-29: closing the launcher while the theme browser remained open kept `vgs:capture` active and kept `SUPER+K` blocked; a copy with an unconditional close reset let `SUPER+K` fire.
- The generated Hyprland close hook resets the active submap when the shell process that owns the mapped overlay is killed. Read in `scripts/smoke/rows/overlay-capture.sh` on host cachy on 2026-09-29: with the real hook, after the row killed the recorded `shell_qs_pid` with SIGKILL, the `vgs:overlay` layer disappeared, `hyprctl submap` returned the default map and `SUPER+K` fired; after the row replaced the close handler with `local _ = layer`, the submap stayed at `vgs:capture` and `SUPER+K` stayed blocked until the row reset it.
- Every dispatch goes through `shell/Core/Compositor.qml`, which runs `hyprctl dispatch` and judges the reply by its text: anything but `ok` is logged with the request. Exit status alone says nothing; a refused dispatcher exits 0 with an error sentence.
- `shell/Core/Dispatch.js` builds every request and speaks both dialects. Each argument must pass its syntax or numeric check, which admits no quote, backslash, space or comma, so no argument ends the Lua string or the classic argument list it is spliced into. Every dispatcher it holds is one a plugin may call through its `compositor` capability; `Dispatch.PLUGIN_DISPATCHERS` is that list. `scripts/test-dispatch.js` pins both syntaxes of every dispatcher and their refusals, with a must-fail control per independent argument rule and per new request form.
- Dispatches wait in order behind one running process. `Dispatch.QUEUE_LIMIT` bounds waiting requests; overflow returns and logs `refused: dispatch-queue=full`. Each reply and exit belongs to the active request until `runningChanged` reports false, including a failed start.
- A Lua session and a classic session take different dispatcher syntax. `Hyprland.usingLua` selects it; a new dispatcher carries both forms. The Lua window dispatchers accept unknown table keys without complaint and `hl.dsp.window.move` answers `ok` for an address that names no window, so only a read of the compositor's state after the reply proves a dispatcher acted.

## Window and pointer operations

The plugin contract fixes the arguments in [the API reference](../../.agents/skills/vgs-plugin/references/api.md#the-shell-object). The builders follow the installed Hyprland 0.56.2 source: [`LuaBindingsDispatchers.cpp`](https://github.com/hyprwm/Hyprland/blob/v0.56.2/src/config/lua/bindings/LuaBindingsDispatchers.cpp), [`LuaBindingsInternal.cpp`](https://github.com/hyprwm/Hyprland/blob/v0.56.2/src/config/lua/bindings/LuaBindingsInternal.cpp), [`DispatcherTranslator.cpp`](https://github.com/hyprwm/Hyprland/blob/v0.56.2/src/config/legacy/DispatcherTranslator.cpp) and [`ConfigActions.cpp`](https://github.com/hyprwm/Hyprland/blob/v0.56.2/src/config/shared/actions/ConfigActions.cpp).

- Classic `fullscreen` takes mode and action but no address. `fullscreenWindow` therefore acts on the focused window in both dialects. It maps `fullscreen` to classic mode `0` and `maximized` to `1`, with `set`, `unset` or `toggle`. A target-specific caller focuses its target and verifies the focus first; the request itself does not bind that focus against a concurrent user change.
- Lua float actions are `enable`, `disable` and `toggle`, unlike fullscreen's `set`, `unset` and `toggle`. Unknown float actions silently toggle. The builder translates the API's action to those Lua values and to classic `setfloating`, `settiled` or `togglefloating`, each with the address selector.
- Lua move and resize take `x`, `y`, `relative = false` and `window`. Classic `movewindowpixel` and `resizewindowpixel` take `exact X Y,address:…`. These forms use absolute layout coordinates or size, not deltas. The layout and the application's size limits still govern the effect; fullscreen windows refuse either action.
- `hl.dsp.focus({ monitor })` and classic `focusmonitor` take the same safe selector subset. The monitor's pointer can take focus back under mouse-focus settings. The nested readback row suppresses mouse focus and warps in its own configuration while focusing its unsized headless output, then restores the configuration.
- `hl.dsp.cursor.move({ x, y })` and classic `movecursor X Y` use absolute layout coordinates. Classic parses each coordinate with `std::stoi`; the judge restricts numeric arguments to canonical decimal integers in its signed 32-bit range. Size arguments also require a positive value.

`scripts/smoke/rows/compositor-dispatchers.sh` drives the existing fixture's compositor provider and reads window flags, position, size, focused monitor and pointer position from the nested compositor. Each effect has a dropped-transport control: the core still receives `ok`, but the same state assertion fails once. No latency budget is measured by this row.
