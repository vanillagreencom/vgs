# Notification ownership

Covers: quickshell/vshell/Modules/Notifications/

VGS is a notification daemon. `Services/NotificationService.qml` registers the freedesktop notification name on the session bus, and every popup, the notification centre, history, rules and grouping are fed by that one registration.

## Boundaries

- Packaging declares that two notification daemons on one session is not a supported configuration, which removes the race before it can happen. Package metadata cannot help a daemon installed outside the package manager, which is what the helper is for.
- The helper (`vshell notifications`) owns detection and the reversible takeover. The shell owns one unasked claim on a fresh install, and thereafter reports the loss where the user is and offers the fix.
- The opt-out setting drives the lazy loader around the notification server, so turning it off destroys the server and releases the name.

## Invariants

1. The bus name is first-come, first-served, and a distribution that ships any notification daemon also ships its activation file — so the first notification sent after login activates that daemon, which then holds the name for the session even with its unit disabled. VGS starts a moment later and loses. That is why the first run claims the name rather than reporting the loss.
2. Detection reads the session bus rather than a list of known daemons: the owner comes from the bus, and the claimants that could win a future session come from every activation file naming the bus in the data directories. A daemon nobody has heard of is still found, and the known-daemon table only supplies a friendly label.
3. Unknown is a first-class state, not a variant of unowned. The bus reports an unowned name as an error, so a failed query is classified — the three phrasings that mean unowned, and everything else becomes unknown with its reason attached.
4. The unit to stop comes from the owning process's cgroup, not from the bus, which reports the session manager for everything on the user bus. A cgroup leaf is not proof of unit ownership either: a daemon started from a compositor rule inherits the compositor's unit, and masking that would end the graphical session. Every mask and stop is gated on the unit's main process being the bus owner, or its start command naming the owner's binary; anything else is reported for the user to act on, with no takeover offered.
5. Shadowing is by file name in the user's own data directory, because activation stops at the first hit in data-directory order. The shadow fails the activation rather than silently starting the daemon the user asked to displace, and a same-named file already there is moved aside, recorded, and moved back by restore.
6. A change that cannot be recorded is a failure. The takeover masks and stops first and writes its undo record last, so it reports failure when the record cannot be persisted — masks and shadows that restore cannot find are not reversible. Winning the bus name is a different claim from succeeding, and the two failures are distinguished: actions that partly landed with the record intact, versus a system changed with nothing to reverse it. Enforced by `scripts/check-notification-takeover.js`.
7. Provenance is the undo record, never a runtime flag and never a settings key. A flag dies with the shell process while the masks persist, and a settings key is a second source of truth that cannot see a record deleted by hand or a restore run from a terminal. The record cannot drift from what needs undoing, because it is what needs undoing.
8. The first-run claim is one shot, and each of its properties is load-bearing. It fires only from a settings file that actually loaded, because a default-valued store is indistinguishable from a fresh install. It fires only once the spend is on disk and read back by another process, because the settings write does not confirm it landed. It is keyed on its own state rather than on whether a conflict exists now, or it would re-fire on every update for anyone whose preferred daemon is a different one. It persists in the user's own settings, so no package upgrade resets it. Every configuration that already existed arrives with it spent. And it is spent on the first usable answer whatever that answer says, or it would fire much later on whichever session the other daemon happened to become stoppable.
9. The announcement of an unasked claim is guaranteed delivery, not best effort: it is the only place the change is explained and the only in-UI pointer at the undo, so its category is exempt from the toast queue cap and from auto-dismissal. The exemption holds at every trim, not only at admission, and a protected entry is never removed unshown. Enforced by `scripts/test-toast-actions.js`, which also requires every undroppable category to be sticky.
10. Opting out reverses what VGS did on its own, because the invariant is that some notification daemon is running afterwards. A takeover the user ran themselves is left alone, a reversal racing the helper is deferred to its exit rather than overlapping it, and provenance not yet known is resolved by the next usable answer rather than guessed at. Where the record was lost, the invariant cannot be held automatically and VGS says so rather than reporting a reversal it did not make.
11. A restore that half worked is reported. A partial restore looks finished while the masks it could not lift are still in force, so the reply carries its failures, and a failed spawn, an unreadable answer or no answer at all raise the same error as an explicit failure.
