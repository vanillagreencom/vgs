# Status actions and secrets

Covers: shell/Core/SecretWriter.qml

The [D061](../decisions/D061-no-manual-commands.md) rule every setup step a user takes follows, on a Settings row, a notice or a dialog; the one-click setup steps a plugin's status entries offer on its Settings page; and the libsecret items the core stores and clears for it. The entries, their values and their rows are [status.md](status.md)'s.

## Setup steps

Consumer text follows [copy.md](copy.md).

A step a user must take to set something up is automatic, or one click: a button on a Settings row, a notice or a dialog. A step that asks a question or needs a privilege opens in a floating TUI or the requirement notice from that button. A secret is typed into a `TextField` with `password` set and VGS stores it. A command a user could run by hand shows only in a `CommandDisclosure` beside that button, never as the instruction itself. The Settings page draws a manifest's status actions and secrets this way ([status.md § Shown](status.md#shown)), and `scripts/check-user-commands.py` fails text that tells the user to run a command: [D061](../decisions/D061-no-manual-commands.md).

## Actions and secrets

- **When.** The value's writer decides when its entry's action applies: a `presence` while `absent`, a `state` while it carries `action: true`. `PluginLogic.statusActionOffered` is the one rule, and an unreported entry offers nothing.
- **Act.** The `manager` capability's `act(id, key)` answers `PluginLogic.statusActionRequest`: `unknown: <id>`, or `refused: action=<key> reason=` `undeclared`, `disabled` or `not-offered`; otherwise the core opens the plugin's own TUI through `TuiRunner.runFor`, judged as the plugin's `shell.tui.run` is, with its answers: `ok`, also for a busy key it focuses, or `refused: tui=<name> reason=...`; or opens the core TUI `core/system` with `apply <step>` for a system step the manifest's `systemSteps` declares, answering as the manager's other core TUIs do and probing the steps again when the run ends ([tui-system.md](tui-system.md)); or raises the requirement notice for the commands through `Notices.chosen`, which no offer's rest holds back, after a scan the press starts, answering `ok` once that scan is asked for: the plugin's value may come from its own probe, later than the last scan, so the notice lists what that scan finds missing, and a full queue is logged as `notices: chosen=<id> refused: notices=full limit=<n>` ([requirement-notice.md](requirement-notice.md)).
- **Own act.** The `status` capability's `act(key)` is the same act for the calling plugin alone: `Capabilities.managerAct` with the caller's id, judged by `PluginLogic.statusActionRequest` and run the same way, so a pane or a flyout offers its own Allow or Install without the `manager` capability. A key of another plugin is one the caller's manifest does not declare, and answers `refused: action=<key> reason=undeclared`.
- **Secrets.** A manifest's `secrets`, `{ service, label }`, needs capability `secrets` and a `presenceList` entry to list its items; `PluginLogic.secretsError` judges it. An item with a `secret` is offered `connect` while `absent` and `disconnect` while `present`, `locked` or `unsafe`, `PluginLogic.SECRET_ACCESS`, and nothing while `unavailable`. The `manager` capability's `storeSecret(id, key, account, secret, done)` and `clearSecret(id, key, account, done)` answer `PluginLogic.secretRequest`: `refused: secret=<account> reason=` `undeclared`, `disabled`, `unlisted` for an account no published item of `key` names, `not-offered` for a verb its access does not offer, or `value` for a secret that is empty, longer than 4096 characters or holds a control character, a line separator or a paragraph separator; `busy` while another write runs.
- **The writer.** `SecretWriter`, in `Capabilities`, runs one write at a time: `secret-tool store --label=<label and account> service <service> account <account>`, the label the `secrets` label, a space and the account, the secret written to its stdin and stdin closed, since secret-tool keeps every byte of a stdin that is no terminal, or `secret-tool clear service <service> account <account>`. `done` receives `{ ok, reason }` and is dropped with the asking instance. Each ended write logs `secrets: <verb>=<id>/<account> ok` or `failed <reason>` and raises the plugin's `shell.secrets.revision`, which its instances read to probe the store again. No secret enters an argv, a log line, a reply or a status value.

## Invariants

1. An action runs only while its value offers it, and only the plugin's own TUI, requirement commands or declared system step; a secret is written only for an account the plugin lists, by the verb its presence offers, and reaches secret-tool on stdin alone. Enforced by `scripts/test-plugin-status.js`, each rule with a control, one of them a copy that puts the secret on the argv; in the nested sandbox, with the host's `vsys` and browser-policy writer hidden from every shell, by `scripts/smoke/rows/settings.sh`, which presses the status fixture's Set up token and Install the tool; the automations row, which presses Enable while logged out; the agent-warden row, Set up and Install vsys; the themes row, Install browser theming; and the notifications row, Connect and Disconnect, reading the stand-in secret-tool's argv and stdin. Each reads a refusal back as its control. `scripts/smoke/rows/system-steps.sh` presses the fixture's own Allow through `status.act` and reads `core/system` opened; its act on another plugin's key reads `undeclared` and starts no terminal, its control. `scripts/smoke/rows/displays.sh` presses Allow in System → Displays. The devtools row reads Install mise withheld and refused while mise is present; its absent case is the fixture's install action.
