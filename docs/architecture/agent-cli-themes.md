# Agent CLI themes

Covers: themes/targets/claude-vgs/, themes/targets/codex-vgs/, themes/targets/gemini-vgs/, themes/targets/hermes-vgs/, themes/targets/omp-vgs/, themes/targets/opencode-vgs/, themes/targets/pi-vgs/, themes/*/apps/claude-*.json, scripts/test-claude-theme.py

The helper renders theme files for the agent CLIs and selects the applied theme in each CLI's own settings file. Palette, overlay, curated-file and output-path contracts are in [theme.md](theme.md).

## Invariants

- A target writes one file from the applied theme unless its configuration says otherwise: `modes` renders its template once per listed mode, and `modeVariants` adds `dark_<role>` and `light_<role>` so one file carries both. A `modes` destination must name the mode; `target_render_passes` in `bin/vshell_helper.py` refuses one that does not, since every mode would otherwise write the same file. The second mode reads the theme's pair when one resolves, otherwise a mode transform of the applied palette; `mode_variant_blueprint` owns that choice, and `transformed_mode_blueprint` carries the package identity onto a transformed variant so a counterpart mode still finds the package's curated files. `theme mode --transform` resolves through the same function, since it asks for the lossy variant even where a pair exists and so cannot go through the chooser. `blueprint_mode_variant` is the lossy primitive underneath and has exactly one caller, so a second copy of the carry cannot appear; `test_the_lossy_variant_has_one_caller_carrying_the_package` in `scripts/test-claude-theme.py` names that caller and `test_the_lossy_transform_keeps_the_package_its_curated_files_live_in` checks what the carry delivers. The agent CLIs that pick a variant from the terminal are the consumers. `test_agent_cli_themes_render_for_every_bundled_theme`, `test_agent_cli_theme_modes_destination_must_name_the_mode` and `test_agent_cli_theme_counterpart_prefers_the_paired_theme` in `scripts/check-vshell-helper.py` check all three.
- Selecting the generated theme inside another app's own settings file writes only the keys that name the theme, and only when one differs, through `set_json_config_key` and `set_yaml_config_key` in `bin/vshell_helper.py`. A hook may create that settings file once its target's theme file is on disk. Three rules govern every such file, the Codex TOML writer included: a created one starts owner-only, an existing one keeps its own permissions, and the write goes through a symlink rather than over it, because these files hold provider credentials, a user can point several account directories at one of them as the owner's three Claude Code accounts do, and they are commonly symlinked into a dotfiles checkout. `resolved_config_path` is where all three writers resolve. The YAML writer is textual and refuses a block shape it cannot read, since VGS ships no YAML dependency. `test_agent_cli_theme_selection_writes_only_the_theme_key` and `test_agent_cli_theme_selection_refuses_a_config_shape_it_cannot_edit` check the key handling; the three file rules run from `SELECTION_CONFIGS`, one row per writer and caller, so a rule cannot be pinned where it does not reach its writer.
- An apply writes both Claude Code themes, `~/.claude/themes/vgs-dark.json` and `vgs-light.json`, and selects the applied theme's mode, when `~/.claude` exists and the `claude` app is on. Each mode is rendered, written and selected on its own, so a theme whose counterpart mode is broken still gets the mode the user applied. The applied theme renders its own mode; the counterpart comes from the pair it declares, else from the mode transform. A theme package's `apps/claude-<mode>.json` merges its `overrides` over the render on both paths, and a per-app override for `claude` merges into the roles first. A curated app file is valid only for the palette it was picked against, so `curated_apps_for_palette` drops the merge-style ones where `load_theme_package` sets `apps`. The test is palette identity, not a list of controls: a package records the `curatedPalette` digest of the palette its merge-style files were picked against in its `theme.json`, `effective_palette_digest` takes the same digest of the palette about to be rendered, and the files are dropped unless the two match. That one comparison answers the restyle slider, a user overlay `colors.toml`, a colour edit written in place, a saved copy and `theme app-colors`. The effective digest folds in the per-app override section of the app that owns the file, because that layer merges into the roles the curated values sit on top of: over the palette map alone it reached one layer short, so a `claude` background override left both digests equal and merged bands picked for the replaced background, which read as body text at 1.04:1 on the diff fill. Only the owning app's section is folded in, so a `btop` override never drops a `claude` file, and a package with no section for that app digests exactly as before. No writer records an override, so a package carrying one never matches and drops, which is the answer wanted: its curated values were picked for a colour the override has replaced. It hashes the colour map rather than the file's bytes, because a slider transforms the map after the file is read and never rewrites it. Naming the controls one at a time instead needed a parameter each and was wrong both ways: inert on a packaged install when `install-system.sh` shipped only bauhaus, roseofdune and targets, so the six existed only as downloads with no built-in copy to compare; and dropping the files of an untouched download of a theme that also shipped built in. Every writer that authors or copies such a file records the digest, which is how a saved copy says what palette its content was built for. `theme duplicate` flattens both layers into one directory, so `duplicate_theme_package` records the digest of the copy's own palette and leaves behind any merge-style file whose layer did not vouch for it; copied as it stood, a legacy overlay `theme.json` became the copy's only record and dropped the built-in file. What becomes of a merge-style curated file a write was not handed is two decisions, and the docstring of `materialize_theme_package` owns both: inside the applied theme's own package the file is not unlinked, and the record the write leaves refreshes only where the layer holds no such file that this write neither wrote nor vouched for. `save_curated_terms` answers what the destination's own palette vouches for, with the per-app override layer left out, and a save writing the applied theme's own package reaches it, `set-wallpaper --save` and `save-current` alike. `applied_palette_parted` compares an applied palette against a package's own at equal rebuild depth, on the reaches its docstring names, and `carry_curated_apps` decides only what the apply paints, under the mode exemption its docstring states. `test_a_save_never_pairs_its_palette_with_a_curated_file_it_did_not_judge` pins the two decisions at the routes it names, and `test_a_save_under_an_override_keeps_the_file_the_override_can_give_back` pins the transform route. A package is two directories, each recording a digest for the files it supplied, so a curated file is matched against its own layer. One digest per package read a legacy overlay as a moved palette, and let a save under a built-in name certify the built-in file it never saw. Every consumer inherits that answer rather than judging again: the apply, the counterpart mode, and the save, which would otherwise bake the mismatch into a package on disk. Dropping does not guarantee the render reads well: a restyled palette misses a named rule in 105 of 486 bundled cases, and akane in light at brightness -100 paints both diff bands `#f2c7ad`. The guarantee is that it is always written rather than refused and every rule it misses is named in the apply warning, so Claude Code never keeps the colours of the theme the user just left. Evaluating a curated file's own rules and falling back only on failure was considered and declined: one theme's file would then be used or not depending on a measurement, which is harder to reason about than this palette-identity test. Only merge-style files are dropped: a replacing curated file is the whole output, and a pointer-style target such as `icons` has no template behind it, so dropping one would leave nothing in its place. A file whose bytes already match is left alone, because Claude Code reloads one that changes.
- A palette can put a diff rule out of reach, which restyle sliders reach often. The closest value the palette allows is written and every missed rule for one apply is named, with its ratio, in one warning on the apply result, which makes the apply partial; the write is never refused, because Claude Code would keep the colours of the theme the user just left. `claude_diff_shortfalls` is the one judge of those rules and runs over the finished token map, after the curated file and the per-app overrides have merged, so a curated band that closes a rule the palette could not reach also closes its warning, and a curated band that breaks one is named. Six light counterparts reach the rules only that way: `akane`, `archwave`, `frankenstein`, `moon-orbit`, `reddcs` and `vice-city` come from the mode transform onto strongly hued backgrounds, which pull both diff bands onto that one hue whatever the generator anchors them to. Three curated-file causes still fail the hook, each naming the theme and the file: a malformed file, a token Claude Code does not carry, and a value no hex colour can be read from, which includes the `rgb()`, `ansi256()` and `ansi:` forms Claude Code accepts but VGS does not write. Every value a file does carry leaves in one spelling, so a curated hex written bare or in upper case is normalised rather than refused. `claude_theme_overrides` in `bin/vshell_helper.py` owns the colours and `scripts/test-claude-theme.py` checks them across every bundled theme, in both modes, shipped and restyled.
- Claude Code's custom themes carry no per-mode values, so the selection is a settings write, through the same shared writer every agent CLI's selection uses. Claude Code applies a theme file's diff colours from 2.1.246; below that version the /diff panel keeps its preset's colours and the rest of the theme still applies.
- Syntax roles (`SYNTAX_ROLE_BASES` in `bin/vshell_helper.py`) carry a hue-preserving lift to 4.5:1 on the background, because Codex paints code and diffs on the terminal's own background and ignores a theme's. The lift writes new roles and leaves every base role unchanged, ANSI or derived: a curated package hands its ANSI colors to app targets verbatim, and a generated palette gets its own ANSI contrast pass. Codex reads the rendered theme only once `[tui] theme` names it, which the `codex-theme` hook sets in `~/.codex/config.toml` without touching another key, keeping that file's own permissions because it holds MCP environment values and provider headers. `test_codex_theme_paints_every_bundled_theme_readably` and `test_codex_theme_selection_changes_only_the_tui_theme_key` in `scripts/check-vshell-helper.py` check both.
