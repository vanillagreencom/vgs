# TUI exit records

Covers: bin/vgsh-tui, shell/Core/TuiRecords.qml, scripts/test-vgsh-tui.sh, scripts/test-tui-logic.js, scripts/qml-tests/tst_tui_records.qml, scripts/smoke/rows/tui.sh

This file holds how the core learns that a floating TUI's run started and ended. How a plugin and the core open a TUI is [tui-capability.md](tui-capability.md). The window, the presentation and the library are [tui.md](tui.md).

## Exit records

The presenter runs inside the terminal, so only it knows when the command ended; a single-instance terminal such as Ghostty starts it from a process that was already running, and `launch` forks the terminal off and returns. The presenter therefore writes the record, and the core reads it.

- Each request the core launches gets a run id, `<ms since the epoch>-<count>`, and hands `launch` the key and the run: `--record <key> --run <run>`. `launch` hands `present` the record directory, `$XDG_RUNTIME_DIR/vgs/tui`, and the app-id and window title it opened the terminal with.
- `present` takes `<stem>.lock`, the key lock, in that directory, `<stem>` being the key with its `/` as `@`, before the logo, and holds it for as long as it lives. A second presenter of the key exits 75 with no logo and no record. It then takes `<stem>@<run>.lock`, the run lock, before it writes the running record, and removes the lock names earlier runs of the key left. The kernel drops each lock with its holder, however it dies, and the command inherits neither, so a process the command leaves behind does not hold the key or delay the run's wait. At its end `present` removes its run lock's name after the ended record is written.
- `present` writes `<stem>@<run>.running.json` before the command runs and `<stem>@<run>.ended.json` once it exits, after the prompt, and on a hang-up or a termination too. Then it removes the key's older ended records, so a key keeps its last ended record, which the state reads after a shell restart. Its own running record stays until the next run of the key or a reap removes it: the core may not have read a file that new, and `FileView` logs a read whose file was removed between its check and its open whatever `printErrors` says (`FileViewReader::read`, Quickshell `41651d7`). The fields, and the code a termination records, are in `bin/vgsh-tui`'s header.
- A record is written whole under a hidden name and moved into place, and never rewritten: a new state is a new file. The core lists the directory with one `FolderListModel`, which notices a name that comes or goes and not a file rewritten under its name, and can miss a change under load ([runtime-qml-folders.md](runtime-qml-folders.md)), and reads each file once with a `FileView` it keeps while the file is listed. The listing is the fast path, not the completion guarantee. `bin/vgsh run` creates the directory before the shell starts.
- `launch` waits for the run's record, polling every 0.05 s for at most 30 s, a ceiling on a terminal's start, not a measurement of one. The core holds the key busy while it waits, so a double click during the terminal's start is refused like one after it. A terminal that never starts the presenter ends the wait as `terminal=silent`, and the request's `done` receives `launcher-failed`.
- After a launcher exits 0, `shell/Core/TuiRecords.qml` starts one `vgsh-tui wait --record <key> --run <run>` process for that run. `wait` opens the run lock, blocks in `flock` until the presenter releases it, and prints the run's ended record. The next run of the key holds only the key lock, so it never delays the wait. If the presenter died after the running record and before the ended record, `wait` takes the key lock, which orders it against `reap` and a later run, and writes the same null-code ended record as `reap` and prints it. A wait for a run the core already saw end can read after the next run of the key removed the run's records; it then exits 3, `reason=gone`. `PluginLogic.tuiWaitOutcome` matches the wait to the runs still awaited by key and run: a gone run no longer awaited is a normal end and logs nothing, and a gone run still awaited logs `tui: wait=<key> run=<run> reason=gone` ([D045](../decisions/D045-tui-wait-holds-a-per-run-lock.md)). The core also starts a wait for each listed running record after a shell restart. It never starts two waits for one run, and a failed wait is not restarted while the same running record stays listed. A wait's ended record stays beside the listing while the listing still holds that run's running record and not its ended one, and the latest of each key stays for the key's state, so a listing stale across later runs of the key cannot show an ended run running again; `PluginLogic.tuiWaitRecordsKept` decides. No timer runs when no run is live.
- A presenter killed outright leaves its running record. `vgsh-tui reap` ends each running record whose key no process holds, with a null code, and only removes one whose run already wrote its ended record. Its record carries the time the reap found the run, which can follow a later run's end, so the core takes a key's last ended run by its start. The core runs it once when it starts and again when a request for a busy key finds no window for the run, one at a time; the reap's lines reach the log as `tui: reaped=<key> run=<run>`.
- The window of a live run is the compositor's one window whose app-id and title are those the record carries. None logs `tui: focus=none tui=<key>`, and more than one logs `tui: focus=ambiguous tui=<key> windows=<n>`; neither focuses anything. Ghostty and kitty keep the `--title` they were given whatever the command prints, and a terminal that ignores the app-id opens a window no record names.
- A `done` belongs to the lifetime of the instance that asked, as the theme runner's callbacks do ([theme-capability.md](theme-capability.md)): a destroyed instance's `done` is dropped, and its run still ends and still moves the state.
- The record holds no log path. A script that keeps a log names it itself through `vgs_tui_log`, and no caller reads one.

Omarchy's `omarchy-update` ends by running `omarchy-update-status`, which tells the shell's update indicator over IPC to refresh, so the script names its caller (basecamp/omarchy `e332dc97`). VGS reads a record the core owns and waits on a lock the core names, so no script needs to know who opened it, and one record serves every caller of the key.

## Invariants

1. A presenter writes its running record before the command and its ended record, with the command's code, when it exits, a termination included, and holds the key lock and the run lock meanwhile, neither of which the command inherits. `wait` blocks on the run lock and then prints or writes the ended record without polling; a later run of the key does not delay it, and a run a later run removed exits with the gone code, never 1. Enforced by `scripts/test-vgsh-tui.sh`, which measured 0 ms on cachy x86_64 on 2026-09-29 from the shell's reap of the presenter to its reap of wait and pins a 1000 ms ceiling (0 means under 1 ms at the measurement resolution), and which repeats back-to-back runs of one key 50 times, with the wait held by SIGSTOP so the order is fixed, with controls that write no ended record, keep a dead presenter's running record, take no lock, hand either lock to the command, skip wait's lock, wait on the key lock, exit 1 for a gone run and skip wait's dead-run end, and by `scripts/smoke/rows/tui.sh`, whose presenter copy that writes no ended record has its run ended by the core's `wait`, with a `done` that answers `vanished`.
2. A running record whose presenter is gone is ended by `reap` or by the run's `wait`, and a live presenter's is not. Enforced by `scripts/test-vgsh-tui.sh`, with controls whose reap ignores the lock and whose wait takes no lock, and by `scripts/smoke/rows/tui.sh`, where the run's `wait` ends a presenter copy's unended run and its `done` answers `vanished`.
3. A wait that ends `gone` for a run the core no longer awaits logs nothing, and one for a run it still awaits logs `reason=gone`; the wait is matched to the awaited runs by key and run. Enforced by `scripts/test-tui-logic.js`, with controls that match by key alone, drop the `reason=gone` line, and log every gone end as a failure. `scripts/qml-tests/tst_tui_records.qml` holds that such a gone end delivers no second `done` and leaves the next run's wait live.
