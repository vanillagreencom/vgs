# The tui capability

Covers: bin/vgsh-tui, shell/Core/TuiRunner.qml, shell/Core/TuiRecords.qml, scripts/test-vgsh-tui.sh, scripts/test-tui-logic.js, scripts/qml-tests/tst_tui_records.qml, scripts/smoke/rows/tui.sh, scripts/smoke/fixtures/plugins/acme.tui/**

This file holds how a plugin and the core open a floating TUI. How the core learns that a run ended is [tui-records.md](tui-records.md). The window, the presentation and the library are [tui.md](tui.md).

## The capability

A plugin declares its scripts as data in the manifest's `tui` key and opens them through `shell.tui`. It never hands the shell a command string.

- `tui: { <name>: { script, title, size, presentation, entry } }`. `<name>` is lower case letters, digits and dashes. `script` is a path under the plugin's `tui/` directory, and no segment is `.`, `..` or hidden. `title` is one printable line of at most 60 characters. `size` is a key of `HyprlandLayer.TUI_WINDOWS`, `default` when absent. `presentation` is `full` or `plain`, `full` when absent. `entry`, when present, is `{ label, icon, group }`: a printable label and group, and a Lucide icon of the shipped set. The key needs capability `tui`. `PluginLogic.tuiError` judges it.
- `bin/lib/check-manifests.js` also reads each script on disk: a regular file with its owner's execute bit, reached through no symbolic link. `bin/vgsh-scan` follows links when it publishes a snapshot, so a link would publish whatever it points at.
- `shell.tui.run(name, args, done)` opens one of the calling plugin's own scripts, from the snapshot of the revision its instance runs ([D014](../decisions/D014-source-revisions-are-published-snapshots.md)), with `args` as argv after the script. `args` is absent or a list of at most 16 strings of 1 to 256 characters, with no control character. `done`, when given, is called once with `{ code, reason }` when the run ends: `reason` is null and `code` the command's exit code, or `code` is null and `reason` is `vanished` for a run `vgsh-tui reap` ended, `launcher-missing` for a launch that found no terminal, or `launcher-failed` for any other launch that ended before the presenter wrote its record. A `done` that is not a function throws `refused: tui=<name> done=not-a-function`.
- `shell.tui.state` is the calling plugin's own scripts, each by name as `{ running, code, endedAt }`: whether a run of it is live, and the code and end time of its last ended run, null before one ended. Every instance of the plugin reads the same state, so a service re-checks after a run a panel started even when the panel was hidden before the run ended.
- `shell.tui.entries` lists every TUI with an `entry`: the core's own, keyed `core/<name>` from `PluginLogic.CORE_TUIS`, and every enabled plugin's, keyed `<plugin id>/<name>`, each as `{ key, plugin, name, title, label, icon, group }`. A disabled plugin's rows leave the list. A launcher lists other plugins' TUIs without naming those plugins ([D005](../decisions/D005-kinds-are-surfaces-no-dependencies.md)).
- A row of `PluginLogic.CORE_TUIS` is `{ argv, title, size, presentation, entry }` with every key set, `entry` null for a row that is not listed. `argv` starts with a file name of the core's `bin/` directory, `vgsh` or `vgsh-<word>`, and `open` runs that file from the `bin/` beside the shell directory, since the shell's `PATH` need not hold the core's commands. `PluginLogic.coreTuiTable` judges the table when the file loads and throws on a defect.
- The core lists the package pickers `core/pkg-install` and `core/pkg-remove` ([packages.md § Pickers](packages.md#pickers)), the passwordless sudo grant `core/sudo-grant` ([tui-sudo.md](tui-sudo.md)), the requirement report `core/doctor` ([requirements.md](requirements.md)), and `core/plugin-add` and `core/theme-add`, which run `vgsh plugin add` and `vgsh theme add` with no URL, so each asks for one with gum input. `core/theme-add` offers to run `vgsh theme apply <name>` after the prompted add succeeds. Omarchy's `omarchy-theme-install` asks for a URL with gum, clones and sets the theme in one command. VGS keeps the clone on the judged add path and asks before it applies the new package.
- `open` refuses a core row with no `entry`. The core opens its own rows with arguments through `TuiRunner.openCore`, judged by `PluginLogic.tuiCore` with `run`'s argument rule, its `done` held for the shell's life: the requirement notice opens `core/requirements-install` so ([requirement-notice.md](requirement-notice.md)), and the `manager` capability opens `core/plugin-update` and `core/plugin-remove` with one installed plugin's id ([settings-window.md](settings-window.md)). A core row's key is `core/<name>` whatever its arguments, so one plugin update runs at a time.
- The launcher's Update row opens the first listed entry of group `Update`, and hides while none is listed.
- `shell.tui.open(key)` opens any listed TUI with no arguments. It answers `ok` once the launcher starts, and for a busy key after the runner asks the compositor to focus the live run's window. The IPC functions `listTuis` and `openTui <key>` and the commands `vgsh tui list` and `vgsh tui open <key>` do the same from outside the shell.
- `run` answers `ok` once the launcher starts, or `refused: tui=<name> reason=` and, in this order, `undeclared`, `disabled`, `args`, `busy` or `launcher-missing`. A request starts no launcher when it is refused, and a refused request's `done` is never called.
- A key is busy from the request that launched it until its run ended: while its launcher waits for the presenter and while its record says running. A request for a busy key asks the compositor to focus the live run's window, through `Compositor.send("focusWindow", ...)`, so a second click raises the open TUI instead of stacking another. `PluginLogic.tuiShownAnswer` is the one judgement of "the TUI is on screen": `open` and the manager capability's TUI members use it to answer `ok` for the busy key they asked for, while `run` and `TuiRunner.openCore` keep the `busy` refusal for callers that need a `done`.
- `shell/Core/TuiRunner.qml` holds the launcher state, `unknown`, `present` or `missing`. It runs `bin/vgsh-tui check`, which uses the same terminal test as `launch`, once when the shell starts. Each probe and each launch that exits 0 sets `present`, and exit 69 sets `missing`. While the state is `missing`, every request that passes the other checks answers `launcher-missing` at once and starts one probe, never two at a time, so a terminal installed later is found by a later request without a restart.
- A launch started while the state was `unknown` or `present` can still find no terminal. It has already answered `ok`, so `PluginLogic.tuiLaunchOutcome` logs `tui: refused: tui=<key> reason=launcher-missing` and the state moves to `missing`.
- `PluginLogic.js` makes every decision: the judge, the argument rule, the busy key, the shared shown answer, the argv, the listed rows, the log lines, the records, the waits, the runs, the state, what each `done` receives and a run's window ([overview.md](overview.md) invariant 6). `scripts/test-tui-logic.js` pins each refusal and shown answer by its text, with a control per rule. `scripts/smoke/rows/tui.sh`, `scripts/smoke/rows/launcher.sh` and `scripts/smoke/rows/manager.sh` read the argv and busy-key answers back from a stand-in xdg-terminal-exec in the nested sandbox.

Omarchy's menu runs each entry's JSONC `action` string, and its bar runs `bash -lc` on a command string. VGS reads the same data from a judged manifest and hands the terminal an argv list, so no plugin text becomes shell code. `presentation: plain` is Omarchy's `omarchy-launch-tui`. Omarchy's launchers `exec setsid`; VGS forks with `setsid -f`, because the shell tracks the launcher it starts (basecamp/omarchy `e332dc97`).

## Invariants

1. A plugin opens only a script its manifest declares, from its published snapshot, and only while it is enabled. While the launcher is `missing`, every request answers `launcher-missing` and starts no launcher. Enforced by `scripts/test-tui-logic.js`, with a control that drops each rule, and by `scripts/smoke/rows/tui.sh` in the nested sandbox, which swaps in a launcher that finds no terminal and then restores it.
2. A run's `done` is called once, from its ended record, with its code, and a destroyed instance's `done` is dropped while its run ends. A lost `FolderListModel` change does not stop completion: `TuiRecords` accepts the wait's ended record in the same event-loop turn as the wait's exit. A request for a live key focuses the run's window. `run` keeps the `busy` answer, while `open` and the manager capability answer `ok` through `PluginLogic.tuiShownAnswer` for the same busy key. Enforced by `scripts/qml-tests/tst_tui_records.qml`, whose stand-in listing drops the ended record's change, by `scripts/smoke/rows/tui.sh`, `scripts/smoke/rows/launcher.sh` and `scripts/smoke/rows/manager.sh` in the nested sandbox, and by `scripts/test-tui-logic.js` with controls that drop the busy mapping or take another TUI's busy key.
