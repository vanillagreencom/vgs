# Backend daemon

Covers: backend/

The backend provides live system integration over a same-user local socket. Its method contract is [../../backend/methods.json](../../backend/methods.json).

## Boundaries

- The runner owns the listener and child processes. The daemon owns registered services. See `backend/internal/runner/` and its tests.
- Theme generation belongs to the helper. Display power belongs to QML's idle service. The backend only schedules wallpaper rotation and reports relevant session events.
- External commands use argv arrays. Credentials and payloads must not enter logs. These are review requirements, not a repository-wide static guarantee.

## Invariants

- Every registered Go method requires an inventory capability. Excluded methods must not be registered; excluded QML references require a removal action. `scripts/check-backend-inventory.py` checks this distinction.
- QML uses advertised methods or capabilities and retains a fallback for unavailable features. `Services/VGSBackendService.qml` owns negotiation; the inventory check rejects raw version comparisons in its scanned callers.
- Capability presence is state. `VGSBackendService.has(name)` answers from the live connection and advertised inventory, so a service built after the backend connected reads the same answer and flips both ways on a backend restart. New consumers bind to it, as the network, session, wallpaper cycling, display, cloud sync, system update and Tailscale services do; the remaining direct readers of `VGSBackendService.capabilities` are not yet converted. `scripts/test-backend-capabilities.js` tests that answer, the Tailscale availability hold and the network service switch.
- The socket rejects other users and requires a runtime directory. See `backend/internal/server/` and its tests.
- A subscribe snapshot is a cached read. `RegisterSnapshot` returns last-known-good state without blocking, or nothing at all before its first successful query; a service whose state comes from an external command registers that query with `RegisterSnapshotRefresh`. That kick must return without waiting and must run the query on the service's own goroutine. `backend/internal/refresh` is the shared loop and cache most services use; tailscale is the exception, coalescing onto its own watcher timer in `backend/internal/services/tailscale/watch.go`. A repeat subscribe re-sends snapshots only for services the previous subscription did not cover, and kicks the refresh only for a service that is newly covered or has nothing recorded yet, so a popout open re-queries nothing it already holds warm while a service whose first query failed is still retried. See `backend/internal/server/` and its tests.
- Each connection owns a bounded outbound queue drained by one writer goroutine, and a connection past the bound is dropped. `Broadcast` never waits on a peer. Coalescing is opt-in: a service declares `CoalesceBroadcasts` only when every one of its broadcasts carries the whole of its state, so a slow reader receives the latest instead of a backlog. A subscribe snapshot is appended whatever the service declares, and dropped when a frame for that service reached the connection after the read began, since that frame is newer than the read. A service that emits distinct events under one name, or a state carrying an edge the shell acts on such as a lock or a suspend flag, does not declare it, and each of its frames is kept. `backend/internal/services/coalescing_test.go` owns the declared set, one row per service, so a declaration cannot be added by an audit that reads one file. See `backend/internal/server/` and its tests.
- A method whose queue is full answers `busy:` instead of blocking the connection's read loop. An idempotent setter registered with `RegisterLatest` keeps one waiting call per coalescing key, shared across connections, and answers a replaced call with a success carrying `superseded`. The key must separate calls addressing different things, such as one display from another, or a write to one is lost to the other. See `backend/internal/server/` and its tests.
- D-Bus access is limited to the registered subscription routes. The inventory and `backend/internal/services/dbusbridge/` define the permitted scope.
- Daemon supervision backs off between restarts and keeps the listener open throughout. A crash loop trips a breaker that holds the backend down for a cool-down which doubles on each trip up to a cap, and then starts it again; supervision never gives up for the session. `SIGUSR1` to the runner, the service's main process, restarts the backend at once with its crash history cleared and leaves Quickshell running: `systemctl --user kill --kill-whom=main -s USR1 vshell.service`. Without `--kill-whom=main` the signal also reaches Quickshell. See `backend/internal/runner/` and its tests.
- A panic in one unit of service work is recovered and logged with its stack through `backend/internal/recovery`, so it degrades that unit instead of ending the daemon. A long-lived loop recovers per event or per tick, so it keeps serving after a fault. A one-shot goroutine or timer callback recovers as a whole. A goroutine that only waits on a process or a channel runs no service code and is not wrapped.
- Long-lived watcher processes start through `execbound.StartChild`. The child gets `SIGTERM` when the backend dies by any means, leads its own process group, and stops by `SIGTERM` then `SIGKILL` to that group after a bounded wait. Starting a gamma adapter first ends any instance of the same program this backend did not start, since two instances fight over the gamma ramp.
- One-shot commands use `backend/internal/execbound`; other long-lived processes require an explicit lifecycle owner. `scripts/check-execbound-adoption.py` checks raw command builders against its lifecycle exceptions. A command whose tool starts children of its own asks for `KillGroup`, which gives it a process group of its own so cancelling it kills the whole fan-out; a command that changes system state keeps the default cancel, which ends the tool alone. The kill runs on the watcher goroutine `os/exec` owns, so a service that cancels a bounded command during shutdown waits for that command to return before its `Close` does.
