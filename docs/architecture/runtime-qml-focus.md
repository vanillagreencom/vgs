# Runtime: QML focus

Covers: shell/Hosts/PluginSlot.qml, shell/Hosts/SummonHost.qml, shell/Hosts/SummonLayer.qml, shell/Hosts/SummonPopup.qml, shell/Hosts/LayerHost.qml, shell/Ui/feedback/Dialog.qml, scripts/qml-tests/tst_dialog.qml, scripts/smoke/app-window.sh, scripts/smoke/rows/layers.sh, scripts/smoke/rows/surfaces.sh, scripts/smoke/rows/windows.sh, scripts/smoke/fixtures/plugins/acme.layers/**, scripts/smoke/fixtures/plugins/acme.surfaces/**

The Quickshell 0.3.1 and Qt facts the shell's QML hosts rest on: how the shell's hosts receive keyboard focus, how Qt Quick moves focus inside a window, and how Qt's Wayland client activates a window when the compositor hands it the keyboard. [runtime-qml.md](runtime-qml.md) holds the other QML facts; [runtime-hyprland.md](runtime-hyprland.md) holds what Hyprland does with the keyboard.

- Omarchy keeps a layer-shell keyboard panel in `WlrKeyboardFocus.OnDemand` after a 75 ms `Exclusive` prime in `shell/Ui/KeyboardPanel.qml` on branch `quattro`, read on 2026-09-30. VGS does not use that pattern for passive layers. `scripts/smoke/rows/layers.sh` proves only that an `acme.layers` passive layer leaves typed keys on the focused helper client while it is mapped. Interactive VGS surfaces use summoned panels.
- `QQuickWindow::focusInEvent` sets the window `contentItem` focus with the activation event's focus reason, after an item may already have been focused before the window became active (`qtdeclarative` 6.11.0 `src/quick/items/qquickwindow.cpp` lines 231-238, read on 2026-09-30). A focus set before a summoned layer window activates can therefore be reported with the activation reason instead of the shortcut reason. Qt then emits `QWindow::activeChanged` after it sends that focus-in event: `QGuiApplicationPrivate::processActivatedEvent` sends `FocusIn` at `qtbase` 6.11.0 `src/gui/kernel/qguiapplication.cpp` lines 2742-2748 and emits `activeChanged` at lines 2769-2773, read on 2026-09-30. `PluginSlot` waits until the host window is active, then focuses the plugin's `initialFocus` with the summon reason. `scripts/smoke/rows/surfaces.sh` reads this on the `acme.surfaces` fixture by verifying a key-summoned panel shows `visualFocus` and `FocusRing`, while an anchored click summon does not.
- Qt Quick moves the focus on Tab and Backtab at the focused item when that item's `Keys` leave the key unaccepted, so the key never reaches a parent's `Keys`. A `FocusScope` that takes the focus again gives it to the child that last held it. `Dialog` keeps the keys inside with `Keys.onTabPressed` on each action and hands the focus to its accept action each time it takes the focus; `scripts/qml-tests/tst_dialog.qml` holds both.
- Qt 6.11.2's Wayland client can lose a keyboard that leaves a window and returns to it in one batch with the reply to the leave's sync. An enter, or the leave of the window last activated, requests a sync unless one is pending, and `QWaylandDisplay::handleWaylandSync` queues a window activation only when the window it wants focused differs from `QGuiApplication::focusWindow()` (`handleWindowActivated`, `handleWindowDeactivated` and `requestWaylandSync` in `src/plugins/platforms/wayland/qwaylanddisplay.cpp`). The `focusWindow()` comparison is the same on qtbase `dev` on 2026-10-01, which also takes an active sub-surface's window as the one wanted. When the leave's sync reply, which queues focus to none, is dispatched in one batch with the enter and the enter's own reply, the second check still sees the window focused and queues nothing, and the queued none then lands: the window holds the compositor's keyboard while `Qt.application.state` reads Inactive, its root item has no focus and typed keys are dropped, until the keyboard leaves and returns. Any return of the keyboard before the client has dispatched the leave's reply can do it, and a busy client dispatches late. Traced with `WAYLAND_DEBUG=client` in the nested sandbox on host cachy on 2026-10-01, twice. With the pointer resting on Settings, where a retile returned the keyboard ([runtime-hyprland.md](runtime-hyprland.md)): `wl_keyboard.leave` on Settings at 58.739723 asked sync 101, and one batch at 58.819826 delivered sync 101's `done`, `wl_keyboard.enter` on Settings and the new sync's `done` at 58.819956; 2 of 60 and 2 of 80 rounds of `scripts/smoke/rows/windows.sh` failed so at load 5 to 7. With the pointer resting off every window, at 12:49:39 UTC: the leave at .2389 asked sync 102, the row's focus dispatch came 72 ms later at .3116, and one batch at .3192 delivered sync 102's `done`, the enter on Settings and its sync's `done`; 1 of 20 rounds failed so at load 4 to 6. QML cannot run Qt's activation again, so `app_window_rows` in `scripts/smoke/app-window.sh` and the keyboard rows of `scripts/smoke/rows/windows.sh` wait, before each dispatch that returns the keyboard to a window, until the window's root item no longer reads `activeFocus`, and for the window to hold the keyboard again before they type.
