# Theme engine

Covers: themes/, bin/, quickshell/vshell/Services/, quickshell/vshell/Modules/Settings/, packaging/install-system.sh, packaging/fedora/vgs-shell.spec

The helper derives palette roles and renders app targets. Theme packages own colour and wallpaper data; shell geometry remains a VGS setting. Who owns the wallpaper on screen, and in what order applies reach the helper, is in [wallpaper.md](wallpaper.md). A curated package's declared UI roles are in [theme-ui-roles.md](theme-ui-roles.md). Agent CLI theme rendering and selection are in [agent-cli-themes.md](agent-cli-themes.md). Wallpaper publishing, downloads and updates from the catalog are in [theme-catalog.md](theme-catalog.md).

## Invariants

- User theme files overlay built-in files individually, except `theme.json`, `colors.toml`, `terminal-colors.toml`, `ui-roles.toml` and `app-colors.toml`, which merge key by key through `package_layer_paths`; `theme.json` keeps `curatedPalette` per layer. `write_user_layer` writes them, keeping the keys that differ from a built-in file, so a package update reaches every value the user did not set. `package_colors_map` reads each `colors.toml` layer under the keys its file wrote and folds the layers through `color_map_tiers` and `merged_color_map`, which arbitrate the slots a key names outright apart from the slots a compound key's last tokens infer. An overlay that omits a key therefore contributes no inferred value over the layer that states that key outright, and the highest layer that states a slot answers for it however the layer below spelled it; `test_package_colours_normalize_once_over_the_merged_layers` checks both. A user `colors.toml` that states `background` or `foreground` outright is the user's own choice and the reader honours it, including a value the earlier per-layer reader inferred from `selection_background` or `selection_foreground` and `shrink_theme_overlays` then wrote as a stated key: no load tells that value from a deliberate one and no pass heals it. Deleting those two lines from `~/.config/vshell/themes/<name>/colors.toml` restores the built-in values and keeps the rest of the overlay, and `theme apply` is what carries them to the shell, which paints from the `theme.json` an apply writes and re-reads no overlay; `theme revert` drops the overlay whole and applies the reverted theme itself when it is the current one. A user `terminal-colors.toml` or `ui-roles.toml` merges only when it holds a top-level `merge = true`; `package_overlay_values` reads both. A file without it replaces the built-in keys: a catalog download installs such whole files, and the writer omits the key when the saved values lack one the built-in file sets, or writes a comment-only mask when they hold none. `theme init` runs `shrink_theme_overlays`, which rewrites a whole-file overlay of a built-in theme through that writer. Curated palettes bypass generated-palette contrast enforcement. A port lists a contrast shortfall it keeps in `theme.json` under `contrastShortfalls`, as `slot`, `ratio` and `floor`. `vshell theme lint` marks the matching warning known and warns on an unmatched entry; `test_lint_reports_listed_shortfalls_as_known` checks both. `--all` exits 1 on unlisted warnings; `test_every_shipped_theme_package_lints_clean` runs it. A save keeps the list, and a rebuild takes it from the applied package; `test_wallpaper_and_save_keep_terminal_slots` checks both.
- A theme package's optional `terminal-colors.toml` holds ANSI slots as a terminal paints them, and nothing else. A slot change that a terminal needs goes there and never in `colors.toml`, because `colors.toml` also feeds the shell's derived roles, pi's interface and the app templates that read slots directly, such as Helix, Emacs, Obsidian and btop. The file's `colorN` entries reach the templates that write a real terminal palette under `terminal_*` role names; every other template keeps the palette's own slot. `terminal_slot_overrides` drops every key that is not one of the sixteen slots. `test_terminal_slot_overrides_reach_terminals_only` in `scripts/check-vshell-helper.py` checks the reach and the exclusion. `test_light_themes_read_in_a_terminal` covers catppuccin-latte, flexoki-light, horizon-light, rose-pine and white: body text and the bands under it at 4.5:1, muted text at 3:1, white's selection fill under body text at 4.5:1, and every other target rendering the same with and without the file. `test_dark_themes_read_in_a_terminal` covers only horizon: effective body slot 15 at 4.5:1 and muted slot 7 at 3:1 against the background, body text on bands 8 and 0 at 4.5:1, and every nonterminal target rendering the same with and without terminal overrides. `test_dark_themes_draw_diffs_in_two_hues` covers every bundled dark theme outside the single-hue palettes: slots 1 and 2, and slots 9 and 10, at least 60 degrees apart in HSL hue, each at HSL saturation 0.15 and 3:1 on the background, with the same render check for each theme that ships the file. The single-hue palettes ship no terminal slots, and their diffs read by the + and - glyphs: most keep red and green in one hue, and fireside's green is near-grey.
- `render_roles` in `bin/vshell_helper.py` is the one place a template's role map gains the terminal slots, and every template render takes its map from it. A slot takes the app's saved `app-colors.toml` override first, under a key `terminal_slot_override_keys` lists: the slot's own `terminal_*` names, then the palette's `colorN` and ANSI name. Then comes `terminal-colors.toml`, then the palette. `app_role_view` reads the same keys, so the App Theming editor shows that override on the slot's `terminal_*` row, and setting the row replaces the slot's other saved keys. `render_template` refuses a placeholder that names a role its map lacks, so a render path that skips `render_roles` fails instead of writing literal placeholder text; a brace token that names no role, such as tmux `#{pane_id}`, passes through. Every rebuild from the current theme takes the applied theme's slots from `with_current_terminal_slots`: a wallpaper change, `save-current`, and a live or saved `apply-colors` edit. Its docstring states which source answers first. A rebuild into the other mode takes none. Restyle adjustments move explicit terminal slots with the palette, each measured against the palette's own mean lightness; `test_restyle_moves_terminal_slots` checks it. A saved package writes the file. A theme saved with no slots removes a stale file, or, under the name of a built-in theme that ships one, writes a file holding no slots so the user overlay masks the built-in slots. `test_terminal_slot_overrides_reach_terminals_only` checks every render path, the override order and the refusal; `test_wallpaper_and_save_keep_terminal_slots` checks the carry and `test_unsaved_applied_theme_keeps_terminal_slots` checks it for an unsaved name; `test_terminal_app_overrides_show_on_their_editor_row` checks the editor row.
- A theme's per-app overrides travel with a save. `save_theme_package` renders the package's editable app files with each app's saved overrides through `render_roles` and writes them to the package's `app-colors.toml`; `theme regenerate` and the first `theme edit-app` seed render with the theme's own overrides too. A save takes its overrides from the first source that answers. First come the overrides carried on a blueprint rebuilt from the current theme: every such rebuild, including `save-current`, `set-wallpaper --save` and `apply-colors --save`, passes through `with_current_terminal_slots`, which carries the overrides of the package whose name or directory exactly matches the shell state's theme name, in the rebuilt mode. A theme applied under a name no package carries has none to carry, and a name that is only part of another package's name matches nothing. Next comes the blueprint's own package; `set-wallpaper --save` under the applied name restores it through `carry_curated_apps`, which resolves it with `applied_theme_package`, the same reader and the same exact name, so it holds the same overrides the rebuild carried. Last comes the package already saved under the destination name, which answers for `import-colors` and `extract-wallpaper --save`, so a save over a package keeps the overrides set on it. `test_save_keeps_app_overrides` checks each source and the exact-name match.
- VS Code's integrated terminal is a terminal: `augment_vscode_colors` writes a package's terminal slots into its bundled curated VS Code theme's `terminal.ansi*` keys. In the package's own mode, a program printing ANSI in VS Code reads the same slots as it reads in ghostty or kitty. A blueprint that did not load supplies no slot and the curated values stand. The bundled copies take each package's saved `[vscode]` overrides too. Each bundled copy takes its label and file slug from the theme package name. The active selection uses that package identity whenever the target installs the package's curated VS Code file. Same-mode wallpaper carries select that bundled package copy. Cross-mode carries and transformed modes also select the bundled package copy, so VS Code keeps the package's original-mode terminal slots, tab label colors, and light or dark base type. A template-rendered file from an extracted wallpaper or a live color change uses a generated identity that no bundled package owns. A duplicate package slug stops the install and names both packages. `test_curated_vscode_theme_takes_the_terminal_palette` checks all of these.
- Curated app files take precedence over generated output, with one exception: a merge-style curated file, which merges into a generated render rather than replacing it, is dropped once the palette is no longer the one it was picked against, whatever moved it. `apps/claude-dark.json` and `apps/claude-light.json` are the ones this covers; [agent-cli-themes.md](agent-cli-themes.md) owns that rule. Every other curated file keeps precedence whatever the palette does. Restyle adjustments leave the stored base palette intact. `curated_file_text` renders them verbatim apart from `{wallpaper}`, so a role placeholder in a curated file stays literal text: a change that must reach a curated file goes through that app's own reconciler, as the VS Code terminal slots do, not through a new placeholder. D017 limits a vendor port to upstream values; that reconciler is one permitted VGS difference and its Current state names the rest. `test_aligned_vendor_ports_take_the_upstream_terminal_palette` holds each `UPSTREAM_TERMINAL_PACKAGES` entry to its upstream VS Code file, pinned by digest.
- An apply commits only what moved, and each target declares what its hooks depend on. Every enabled target renders into memory before any destination is touched, so a template or curated file that cannot be read costs its own target and not the apply, and a target that cannot render whole writes none of its files. `write_file` in `bin/vshell_helper.py` then replaces each destination and reports whether its bytes changed. A target's `reloadHook` in its `config.json` is a verb that tells a running application to re-read a file that target wrote, so it is sent only when those bytes moved. `test_every_target_hook_is_dispatched_and_classified` holds the set under each key against the shipped configs, so moving a name between the two keys reddens rather than changing an apply silently. A target's `hook` asserts wiring no destination of that target carries, such as the icon-theme gsettings key, btop's selected `color_theme` or a VS Code variant installed since the last apply, so it runs on every apply that reaches that target's commit; a target whose render or write failed sends neither of its hooks, since a file that is not on disk must claim neither a reload nor a wiring assertion. Most of those hooks compare their own inputs and return without writing when the state is already right; `pi-theme-link` re-asserts its wiring unconditionally. Re-applying a theme is therefore what re-runs a hook that failed. A target declaring both keys runs its `hook` first, because the wiring has to be in place before the verb that makes the consumer re-read it. A wallpaper pick that keeps the palette moves only the targets whose template names the wallpaper role, `themes/targets/vgs-shell/vgs-theme.json` (as `{wallpaper.ref}`) and `themes/targets/pywalfox-vgs/colors.json` (as `{wallpaper}`); a pick that extracts a palette from the image re-derives every role and moves every target. A destination that cannot be written becomes one warning naming its target while every other target still lands, and a stale curated artifact that cannot be removed costs only that artifact, since removing it is what exposes the generated output beneath. `theme-current.json` is written before the hooks, so a failing hook cannot leave the shell showing a theme the next rebuild from the current theme does not start from. The apply result reports the written subset as `changed` beside the full `rendered` list. `test_write_file_reports_whether_the_destination_moved`, `test_theme_apply_runs_only_the_reload_hooks_whose_target_changed`, `test_theme_apply_runs_a_failed_hook_again_on_the_next_apply`, `test_theme_apply_commits_a_curated_target_as_one_unit`, `test_theme_apply_lands_every_other_target_when_one_target_fails` and `test_the_shipped_wallpaper_templates_are_the_ones_the_documented_invariant_names` in `scripts/check-vshell-helper.py` check the write's report, the two hook contracts, the per-target containment, the curated unit and that ordering.
- Generated target paths are VGS-named and are declared in each target's configuration. Review path changes against the consumers; no checker proves compatibility.
- Theme applies carry distinct request ids and failed reads retain an explicitly identified displayed result. `scripts/test-theme-requests.js` checks request handling.
- `theme list --json` reports `preview`, the image the settings Current Theme card, the Dash Themes tab and the theme switcher all paint. `theme_preview` in the helper is its one owner: the package's `preview.jpg` whether or not the user edited the theme, else a palette card drawn into `~/.cache/vshell/theme-previews/`, keyed on the colours it paints and encoded with `zlib` alone, else empty for a theme with no palette. No shell path renders a preview; `scripts/capture-theme-previews.py` captures the shipped screenshots from a Hyprland session, as [D020](../decisions/D020-drawn-theme-preview-fallback.md) records. The list reports `themes/thumbnails/<name>.jpg` apart as `thumbnail`, which a surface paints only as a placeholder. The same list removes every cached card no listed theme names. `test_theme_list_reports_the_preview_and_the_thumbnail_apart` in `scripts/check-vshell-helper.py` checks both fields, the card's decoded pixels with no tool on `PATH`, a new card after a colour edit, and the pruning.
- A star is `starred: true` in the theme's overlay `theme.json`; `set_theme_starred`, behind `theme star` and `theme unstar`, sets and clears it. `THEME_META_BOOKKEEPING_KEYS` marks it as filing, not an edit: `user_layer_files` skips a `theme.json` holding only such keys, so a star raises no modified badge and keeps the shipped screenshot; `drop_theme_overlay` keeps them through `theme revert`; `duplicate_theme_package` drops them from a copy. The switcher's Starred list and the Dash Themes tab read the star from `theme list --json`. `test_theme_list_reports_installed_wallpapers_and_the_star` checks the store, the flags, the revert, the copy, and an unstar beside restyle adjustments.
- Reading the current theme never applies one. With no `theme.json` the helper answers with the file an apply of the default theme would write, rendered from the `vgs-shell` target without writing it, and `theme init`, which `VGSThemeService` runs at startup, is the explicit first-run apply. `test_current_theme_reads_without_applying` and `test_theme_init_applies_only_without_state` in `scripts/check-vshell-helper.py` check both; `scripts/test-theme-startup.js` checks that startup runs `theme init` before its first reads.
