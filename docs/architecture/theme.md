# Theme engine

Covers: themes/, bin/, quickshell/vshell/Services/, quickshell/vshell/Modules/Settings/

The helper derives palette roles and renders app targets. Theme packages own colour and wallpaper data; shell geometry remains a VGS setting.

## Invariants

- User theme files overlay built-in files individually. Curated palettes bypass generated-palette contrast enforcement. See theme composition and palette derivation in `bin/vshell-helper`.
- A theme package's optional `terminal-colors.toml` holds ANSI slots as a terminal paints them, and nothing else. A slot change that a terminal needs goes there and never in `colors.toml`, because `colors.toml` also feeds the shell's derived roles, pi's interface and the app templates that read slots directly, such as Helix, Emacs, Obsidian and btop. The file's `colorN` entries reach the templates that write a real terminal palette under `terminal_*` role names; every other template keeps the palette's own slot. `terminal_slot_overrides` drops every key that is not one of the sixteen slots. `test_terminal_slot_overrides_reach_terminals_only` in `scripts/check-vshell-helper.py` checks the reach and the exclusion. `test_light_themes_read_in_a_terminal` covers catppuccin-latte, flexoki-light, rose-pine and white: body text and the bands under it at 4.5:1, muted text at 3:1, white's selection fill under body text at 4.5:1, and every other target rendering the same with and without the file.
- `render_roles` in `bin/vshell-helper` is the one place a template's role map gains the terminal slots, and every template render takes its map from it. A slot takes the app's saved `app-colors.toml` override first, under a key `terminal_slot_override_keys` lists: the slot's own `terminal_*` names, then the palette's `colorN` and ANSI name. Then comes `terminal-colors.toml`, then the palette. `app_role_view` reads the same keys, so the App Theming editor shows that override on the slot's `terminal_*` row, and setting the row replaces the slot's other saved keys. `render_template` refuses a placeholder that names a role its map lacks, so a render path that skips `render_roles` fails instead of writing literal placeholder text; a brace token that names no role, such as tmux `#{pane_id}`, passes through. A wallpaper change and `save-current` carry the slots, and a saved package writes the file, or removes a stale one when the theme carries no slots. A theme's preview cache key covers its terminal slots, since the preview's terminal draws them; `test_preview_key_covers_terminal_slots` checks it. `test_terminal_slot_overrides_reach_terminals_only` checks every render path, the override order and the refusal; `test_wallpaper_and_save_keep_terminal_slots` checks the carry; `test_terminal_app_overrides_show_on_their_editor_row` checks the editor row.
- VS Code's integrated terminal is a terminal: `augment_vscode_colors` writes the theme's terminal slots into a curated VS Code theme's `terminal.ansi*` keys, so a program printing ANSI there reads what it reads in ghostty or kitty rather than the curated theme's own guess. A blueprint that did not load supplies no slot and the curated values stand. The bundled copies the VS Code extension installs take each theme's saved `[vscode]` overrides too, so they match what the apply hook writes. `test_curated_vscode_theme_takes_the_terminal_palette` checks all of these.
- Curated app files take precedence over generated output. Restyle adjustments leave the stored base palette intact. `install_curated_file` copies them verbatim and renders only `{wallpaper}`, so a role placeholder in a curated file stays literal text: a change that must reach a curated file goes through that app's own reconciler, as the VS Code terminal slots do, not through a new placeholder. See app-target rendering and restyle handling in `bin/vshell-helper`.
- A target writes one file from the applied theme unless its configuration says otherwise: `modes` renders its template once per listed mode, and `modeVariants` adds `dark_<role>` and `light_<role>` so one file carries both. A `modes` destination must name the mode; `target_render_passes` in `bin/vshell-helper` refuses one that does not, since every mode would otherwise write the same file. The second mode reads the theme's pair when one resolves, otherwise a mode transform of the applied palette; `mode_variant_blueprint` owns that choice, and carries the package identity onto a transformed variant so a counterpart mode still finds the package's curated files. The agent CLIs that pick a variant from the terminal are the consumers. `test_agent_cli_themes_render_for_every_bundled_theme`, `test_agent_cli_theme_modes_destination_must_name_the_mode` and `test_agent_cli_theme_counterpart_prefers_the_paired_theme` in `scripts/check-vshell-helper.py` check all three.
- Selecting the generated theme inside another app's own settings file writes only the keys that name the theme, and only when one differs, through `set_json_config_key` and `set_yaml_config_key` in `bin/vshell-helper`. A hook may create that settings file once its target's theme file is on disk. Three rules govern every such file, the Codex TOML writer included: a created one starts owner-only, an existing one keeps its own permissions, and the write goes through a symlink rather than over it, because these files hold provider credentials, a user can point several account directories at one of them as the owner's three Claude Code accounts do, and they are commonly symlinked into a dotfiles checkout. `resolved_config_path` is where all three writers resolve. The YAML writer is textual and refuses a block shape it cannot read, since VGS ships no YAML dependency. `test_agent_cli_theme_selection_writes_only_the_theme_key` and `test_agent_cli_theme_selection_refuses_a_config_shape_it_cannot_edit` check the key handling; the three file rules run from `SELECTION_CONFIGS`, one row per writer and caller, so a rule cannot be pinned where it does not reach its writer.
- An apply writes both Claude Code themes, `~/.claude/themes/vgs-dark.json` and `vgs-light.json`, and selects the applied theme's mode, when `~/.claude` exists and the `claude` app is on. Each mode is rendered, written and selected on its own, so a theme whose counterpart mode is broken still gets the mode the user applied. The applied theme renders its own mode; the counterpart comes from the pair it declares, else from the mode transform. A theme package's `apps/claude-<mode>.json` merges its `overrides` over the render on both paths, and a per-app override for `claude` merges into the roles first. A file whose bytes already match is left alone, because Claude Code reloads one that changes.
- A palette can put a diff rule out of reach, which restyle sliders reach often. The closest value the palette allows is written and every missed rule for one apply is named, with its ratio, in one warning on the apply result, which makes the apply partial; the write is never refused, because Claude Code would keep the colours of the theme the user just left. Three curated-file causes still fail the hook, each naming the theme and the file: a malformed file, a token Claude Code does not carry, and a value no hex colour can be read from, which includes the `rgb()`, `ansi256()` and `ansi:` forms Claude Code accepts but VGS does not write. Every value a file does carry leaves in one spelling, so a curated hex written bare or in upper case is normalised rather than refused. `claude_theme_overrides` in `bin/vshell-helper` owns the colours and `scripts/test-claude-theme.py` checks them across every bundled theme, in both modes, shipped and restyled.
- Claude Code's custom themes carry no per-mode values, so the selection is a settings write, through the same shared writer every agent CLI's selection uses. Claude Code applies a theme file's diff colours from 2.1.246; below that version the /diff panel keeps its preset's colours and the rest of the theme still applies.
- Generated target paths are VGS-named and are declared in each target's configuration. Review path changes against the consumers; no checker proves compatibility for all consumers.
- Syntax roles (`SYNTAX_ROLE_BASES` in `bin/vshell-helper`) carry a hue-preserving lift to 4.5:1 on the background, because Codex paints code and diffs on the terminal's own background and ignores a theme's. The lift writes new roles and leaves every base role unchanged, ANSI or derived: a curated package hands its ANSI colors to app targets verbatim, and a generated palette gets its own ANSI contrast pass. Codex reads the rendered theme only once `[tui] theme` names it, which the `codex-theme` hook sets in `~/.codex/config.toml` without touching another key, keeping that file's own permissions because it holds MCP environment values and provider headers. `test_codex_theme_paints_every_bundled_theme_readably` and `test_codex_theme_selection_changes_only_the_tui_theme_key` in `scripts/check-vshell-helper.py` check both.
- Enabling per-monitor wallpaper mode preserves each screen's current image and disables retained cycling. `scripts/test-switcher-scope.js` checks the transition.
- Theme applies carry distinct request ids and failed reads retain an explicitly identified displayed result. `scripts/test-theme-requests.js` checks request handling.
- A theme downloads as one archive from its `themes-vN` release, accepted only at the catalogued size and sha256, then unpacked member by member under the manifest path rule. `_catalog_fetch_verified` and `_catalog_unpack` in `bin/vshell-helper` own acceptance; `scripts/gen-theme-catalog.py` checks the generated catalog and the release pin.
- The archive streams into `~/.cache/vshell/theme-assets/` in fixed chunks, hashed as it is written, so the verified bytes are the bytes the unpack step reads back and no install holds a whole archive in memory. It is deleted once the install finishes, so the cache holds in-flight downloads only. An installed theme is composed from local directories alone, so applying it makes no network call.
- Each lock entry binds its archive to the definition files it packed. `scripts/gen-theme-catalog.py --check` refuses a catalog whose committed definitions differ from the pinned archive, and `--check-assets-published`, which CI runs, refuses a pin whose archive is not an asset of a release that exists.
- An uninstalled theme paints from `themes/thumbnails/<name>.jpg`, which ships with the package that every install carries. `theme_shipped_preview` in the helper is the one answer to what can be painted without rendering. Both callers, the catalog browser through `catalog_entries` and `theme list --json`, pass the package's own `preview.png` when it has one, and both resolve the thumbnail through `theme_thumbnail_path`.
- Reading the current theme never applies one. With no `theme.json` the helper answers with the file an apply of the default theme would write, rendered from the `vgs-shell` target without writing it, and `theme init`, which `VGSThemeService` runs at startup, is the explicit first-run apply. `test_current_theme_reads_without_applying` and `test_theme_init_applies_only_without_state` in `scripts/check-vshell-helper.py` check both; `scripts/test-theme-startup.js` checks that startup runs `theme init` before its first reads.
- Download publication holds the mutation lock only around the directory swap. Removal requires matching download identity. See `catalog_download_theme` and `catalog_owns` in the helper.
