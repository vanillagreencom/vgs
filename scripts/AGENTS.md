# scripts/

Validation and measurement scripts. A script here reads the repository and the nested sandbox. Nothing under `bin/` or `shell/` may load a file here, since an install ships without `scripts/`: a helper the runtime needs goes in `bin/lib/`, and the `runtime_reads_no_scripts` check in `validate` refuses the load.

- A check is a row in `scripts/validate` with its must-fail control beside it, named `test-<subject>` for the script it exercises. `qml-smoke.sh` is a runner and has none; the checks `validate` makes itself have theirs in `test-validate.sh`. A new row whose inputs match a case's file in `test-validate.sh` adds its command to that case's expected plan.
- What the sandbox needs, how it exits and where the shell's log is: `docs/architecture/validation-smoke.md` and `docs/architecture/runtime.md` § Process.
- What a memory figure may claim and how the sampler finds the shell: `docs/architecture/memory.md`.
- Use `scripts/validate --list` to inspect the affected checks, then omit `--list` to run them once. Selection defaults to the default branch's merge base; `--changed BASE` narrows a fix round, and `--full` explicitly requests every row. The input globs beside each manifest row include its shared dependencies. An unmapped source input selects the full area; docs and harness-only changes do not start the product smoke.

- `arch-packages.sh` builds and installs the Arch recipes in a podman container, the `package` area of `validate`. It is a runner like `qml-smoke.sh`; `check-packaging.js` is the recipes' offline check and has its control.
- `lib/release-tarball.sh` is the one builder of a VGS source tarball. A script that needs one calls it: `docs/architecture/distribution.md` § Release tarball.
- `release` and `publish-aur.sh` are the maintainer's release tools: they publish to GitHub and the AUR with the maintainer's own keys, so an agent runs them only with `--dry-run`. `docs/RELEASING.md` holds the flow; `test-release.sh` and `test-publish-aur.sh` are their controls.
- `readme-install.sh` runs the commands of the README's install section in clean podman containers, by hand before a release. It is a runner like `qml-smoke.sh`; `check-readme.js` is the README's offline check and has its control, and `test-readme-install.sh` covers the runner's host side. What the section must say and how the runner treats an unpublished command: `docs/architecture/install-guide.md`.
- `landing-times.py` is a measurement script, not a check. It reads GitHub repository activity through `gh` and reports landing duration lines plus medians for all landings, push landings, pull-request landings and wait time.
- `sandbox-shots.sh` captures the sandbox's surfaces as PNGs under `tmp/` for visual evidence. It is a runner like `qml-smoke.sh`; its capture guards in `smoke/shot.sh` and its host window reader in `smoke/host-window.sh` have their control.
- `readme-shots.sh` makes the plugin README images from `docs/images/plugins/shots.tsv` through `sandbox-shots.sh`; `test-readme-shots.sh` is its control and `check-readme-images.py` the images' offline check: `docs/architecture/readme-images.md`.
- Smoke rows live under `scripts/smoke/rows/`. The runner fixes their order because later rows use earlier state. Only `scripts/smoke/harness.sh` owns the sandbox lifetime; its teardown lives in `scripts/smoke/teardown.sh`, which it sources.
- `scripts/smoke/Probe.qml` holds the disposable instance readers. The Gallery's component and focus readbacks follow [components-gallery.md](../docs/architecture/components-gallery.md); shipped components contain no test-only readers.
- Smoke fixtures live under `scripts/smoke/fixtures/plugins/`. Offline validation checks every fixture. Runtime refusal fixtures belong to the rows that assert their refusal. `scripts/smoke/fixtures/tui/<id>/tui/` holds the TUI scripts a row plants into its copy of a shipped plugin: the smoke's stand-in terminal runs no TUI script but one of these or a fixture plugin's own ([validation-smoke-host.md](../docs/architecture/validation-smoke-host.md)). `scripts/smoke/fixtures/slack/` is not a plugin: it is a synthetic Slack configuration, a workspace list and one disk-cache entry, that the notifications row and `sandbox-shots.sh` place under the sandbox's configuration. `scripts/smoke/fixtures/devices/` holds the device fakes' programs and configuration, which `scripts/smoke/devices.sh` starts ([validation-smoke-devices.md](../docs/architecture/validation-smoke-devices.md)). `scripts/smoke/fixtures/updates-status.json` is the updates snapshot `sandbox-shots.sh` plants, stamped with the time it is planted, so the updates service runs no check.
